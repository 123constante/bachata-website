## Must fix

### B1b. A preview in flight, then − and + inside the debounce, still sticks on Checking
Sequence (code applied on basket K1, so `lastApplied.key = K1`):
1. Tap +. The key becomes K2, `step()` sets Checking, and the timer fires after 400 ms: `pricePromo` sets `pricedKey = K2` and the K2 request is **in flight**.
2. Tap − before the reply. The key is K1 again. The effect sees `pricedKey (K2) !== K1`, does `promoSeq += 1` (so the K2 reply will be dropped) and schedules a K1 timer.
3. Tap + within 400 ms. The key is K2 again. The cleanup clears the K1 timer. The effect now sees `pricedKey === K2`, so it takes the new restore branch, but `lastApplied.key` is K1, not K2, so nothing is restored. It returns.
4. The K2 reply arrives, `seq !== promoSeq.current`, and it is dropped. `promo` stays `checking` for good, no request is pending, and Continue says "Wait while the promo code is checked." The only way out is Remove.

**Reproduced** on 9a7e44842 with a probe test in a scratch worktree (not committed). Steps: apply SAVE10 on one Full Experience; make `previewPromo` return a deferred promise; `add`; wait until `previewPromo` is called once; `Remove one` then `add` back to back; resolve the deferred; wait 1.2 s. Result: stub text `SAVE10Checking…Remove`, `previewPromo` calls = 1.

The root cause: `pricedKey` is "the basket the latest preview was **asked** for", but the reply for it can be discarded later by a `promoSeq` bump. When that happens, `pricedKey === key` no longer means an answer exists.

Suggested fix, either one:
- in the `pricedKey.current === key` branch, when `promo.status === 'checking'` and there is no `lastApplied` for this key, fall through and schedule a preview instead of returning; or
- in the effect's scheduling path (the one that bumps `promoSeq` and so orphans the in-flight reply), set `pricedKey.current = null`, so a return to that key re-prices.

Add the probe as a second regression test (it fails on 9a7e44842).

## Checklist (brief items)

1. **B1 fixed: PASS for the round-1 sequence, FAIL for B1b.** With Checking on the priced key, the effect restores `lastApplied` (`setPromo(last)`). No timer or preview runs, because the branch returns before `promoSeq += 1`. Continue is unblocked, because `promoView` sees `applied` with `state.key === key`. The B1b variant above is not covered.
2. **lastApplied cannot restore a stale answer: PASS.**
   - *Key mismatch:* the restore requires `last.key === key`, and `key` is the full `pickerPromoKey` (basket, night, paid-line list prices). A types refetch with new prices changes the key, so nothing is restored.
   - *After Remove:* `removePromo` sets `lastApplied.current = null`.
   - *After a refused re-price:* refused sets `stubbed=false`, so `liveCode` is null and the effect returns before the restore branch. A later Apply runs with `stubbed=false` (liveCode stays null) until the new reply is ok, so the old `lastApplied` is never consulted mid-check.
   - *Different code:* the input and Apply are not rendered while the stub shows (`stubbed && applied|checking`). So the code cannot change under `lastApplied`; Remove (which clears the ref) is the only route to a new code.
   - A restored answer is exactly what the server priced for this key, so it is never a discount priced for a different basket. What the client sends then still faces checkpoint (b).
3. **setHeld(null) on Apply/Remove: PASS.** A held `price_changed` was priced with or without the old code. Clearing it means the next Continue sends the client total (promo or list) and, if that disagrees with the server's effective price, reserve v5 returns `price_changed` with no order and the hold comes back. It can cost one extra round, never a wrong charge. This fixes round-1 N1 (the bar no longer shows a discounted held total after Remove). See N4.
4. **Regression test: PASS.** The head's `ticketPickerB1.test.tsx` was copied into a scratch worktree at `cc1c7b29f`: `promo: + then - inside the debounce restores the applied code` **fails** there (1 failed, 24 passed). At `9a7e44842`: 25/25 pass.
5. **No new money-path risk: PASS.** The delta touches only client state (`lastApplied` ref, restore branch, two `setHeld(null)`). `buildPickerBody` precedence (held, then promo, then list) and the `promoView` gating are unchanged.
