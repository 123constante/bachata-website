Findings:

1. scripts/lib/bot-pr-adopt.mjs:59, low (drift). Only `openPrs[0]` is checked. The admin version
   returns none + warning when more than one PR is open. Scenario: the branch has a bot PR into
   main and an owner PR into another base (GitHub allows one open PR per head+base pair). If the
   bot PR is listed first, the owner PR is skipped with no warning. If the owner PR is first, it
   is replaced while a second PR is open. Neither closes the wrong PR. Fix: treat
   `openPrs.length > 1` as skip + warn, as admin does.

2. scripts/lib/bot-pr-adopt.mjs:90-91, low. A label-copy or comment failure after a successful
   create throws, so the step goes red (good). But the next push sees the bot PR and skips, so
   the labels (for example `automerge-ok`) are never copied and the old PR never gets its
   "Replaced by" comment. The log names only the failed call. Fix: put the old label list in the
   error text so a person can re-apply it.

3. scripts/lib/bot-pr-adopt.mjs:60, nit (drift). The author check is case-sensitive. Admin
   lowercases. `github.repository_owner` is the canonical login, so this is harmless today.

4. scripts/lib/bot-pr-adopt.mjs:60, nit (drift). This version does not call `GET /user` to learn
   the bot login, and it does not warn on a third-party author. Any non-owner PR is logged as
   "Already has an open PR" and skipped. This is safe (it fails toward doing nothing). Only the
   warning is lost.

5. Behaviour, nit (operational). The replacement does not carry reviews/approvals,
   conversation comments, assignees, reviewers, milestone or auto-merge state. Commit statuses
   stay with the SHA. A local session that opened an owner-authored PR on a claude/** branch
   gets it closed and re-numbered on its next push, so its stored PR number then points at a
   closed PR. CLAUDE.md still describes owner-authored PRs as valid (bot approves). Confirm
   that this replacement is wanted for local sessions too, not only cloud workers.

6. .github/workflows/bot-pr.yml:58, nit (bootstrap). A push event runs the yml from the pushed
   branch, but the script comes from the main checkout. Until this PR merges, any push to a
   branch that carries the new yml fails with "Cannot find module scripts/lib/bot-pr-adopt.mjs".
   After the merge, claude/** branches cut earlier keep the old yml and get no adoption until
   they are rebased. This is expected, but worth knowing when you test the first adoption.

7. .github/workflows/bot-pr.yml:59, nit. If the script exits 0 without writing adopt.out (the
   isEntryPoint fail-open on a junction or symlink path, which cannot happen on ubuntu-latest),
   `$(cat adopt.out)` fails inside the test. The step then exits 0 silently. Admin has the same
   pattern. Optional fix: `[ -f adopt.out ] || { echo "::error::adopt.out missing"; exit 1; }`.

Pre-existing, not introduced here: a push-triggered workflow reads BOT_PR_TOKEN from the
workflow file of the pushed branch. secrets-register.json already grandfathers this (A34 drill).
