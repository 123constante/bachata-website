## Findings (most severe first)

### F1 (Low) A refetch failure after a successful load hides the stat while the list still shows rows
`src/pages/OrganiserProfile.tsx:1388-1391`. The strip filters on `upcomingFailed` /
`pastFailed` alone (`:1138-1139`), while the error lines are gated on the same flag AND
an empty list (`:1497`, `:1570`). React Query keeps the last successful `data` when a
later refetch fails (window focus, a "Try again" that fails, a background retry), so in
that state `isError` is true and the list still renders the retained rows. Result: the
"Upcoming dates" (or "Past nights") stat disappears from the strip while the section
below still lists those dates and shows no error line. Not a false number (the brief's
rule holds), just a strip/section inconsistency in a rare state. Options: gate the stat
on `failed && list.length === 0` to match the error lines, or leave as is. Not covered
by the matrix (it never moves a feed from success to error).

### F2 (Info) Team feed failed: the third stat silently substitutes an events stat
`src/pages/OrganiserProfile.tsx:1171-1172,1390`. With the team feed in error and
`orderedTeam` empty, the third stat falls through to "Yrs active" / "Since" computed from
the healthy events feed. For an organiser that has a team, the strip shows a different
(true) stat instead of the team count, next to the team error line. Correct under the
brief (no number for the failed feed) and arguably the right call; noted so the owner
knows the strip changes shape, not just hides.

### F3 (Info) `BROWSER_NO_STORE` is the name of a header that is not `no-store`
`app/detailLoader.ts:91`: `const BROWSER_NO_STORE = "public, max-age=0, must-revalidate"`.
The r1 F4 wording came from this constant's name. The PR's comment fix is right; the
constant name is the thing that will mislead the next reader. Out of this PR's scope
(not in the diff); a rename is a one-liner for a later tidy.

## Judge items

### (1) Strip never shows a number for a failed feed; healthy zero unchanged
Code: `OrganiserProfile.tsx:1384-1391`. Per-stat `failed` flags, then
`.filter((s) => !s.failed)`:

| failure | Upcoming dates (`upcomingFailed = events || future`) | Past nights (`pastFailed = events || past`) | third stat |
|---|---|---|---|
| future (upcoming) feed | hidden | shown | shown (not derived from future occs) |
| past feed | shown | hidden | shown (not derived from past occs) |
| events feed | hidden | hidden | hidden iff no team AND no `founded_year` |

The third-stat gate is exact: `sinceYear` (`:906-918`) reads only `allEvents`, and
`estYear` (`:1167`) uses `foundedYear` first, so the stat is events-derived only when
`orderedTeam.length === 0 && foundedYear === null`. A team count or a founded-year
"Yrs active" is unaffected by an events failure and stays visible. Verified by the matrix
(27 rows + "events failed" + "events failed + healthy team") and by inspection.

Healthy zero: before the fix the strip rendered the value unconditionally, so a real
zero showed `0` (and a no-year organiser `-- Since`). There is no "hide-empty-stat rule"
in this strip, as the handover says. After the fix a healthy zero still renders `0`:
`failed` is false, value untouched. Pinned by the "healthy zero" test (`:208-213`) and
by every matrix row with an `empty` feed (expects `'0'`, `:164,166`). Unchanged, as the
brief required. Owner decision stands if a healthy zero should also hide.
