## Findings

### (1) serverToday.ts

**N1 (nit, should fix): `HEAD /` is not a cheap, plain request on this deployment** (`src/modules/tickets/serverToday.ts:26`).

- `vercel.json` sends `/` to `/city/london-gb` with a 307. `app/routes/index.tsx` does the same in its loader, and `fetch` follows the redirect by default.
- The followed request hits `/city/:path*`, which is in the Edge Middleware matcher (`middleware.ts:28-73`). That costs one middleware invocation per ticket-screen load, even though it returns `next()` for humans.
- It then reaches the on-demand SSR + ISR home route (`app/routes/home.tsx`). On a cache miss the loader runs its Supabase queries just to produce a `Date` header.
- The `Date` on an edge-cached ISR hit may be the time the cache was filled, not the current time; Vercel's behaviour here is not verified. This can only make "today" lag. At worst, yesterday's ticket stays under Upcoming for up to the cache TTL just after London midnight. It can never hide tonight's ticket, because a stale `Date` is never in the future.
- I could not check this live, because the sandbox proxy returned 403 for `www.bachatacalendar.co.uk`. So I cannot confirm whether the HEAD gets a 405 from the SSR handler, either.
- Suggested fix: `HEAD` a static file in `public/` that has no redirect and no middleware match (e.g. `/robots.txt` or `/favicon.ico`), with `redirect: 'manual'` or just that path.

**N2 (nit, should fix): no timeout on the clock request** (`src/modules/tickets/serverToday.ts:26`, `src/modules/dancer-app/screens/tickets/useTicketCard.ts:69`).

- `useTicketCard`'s `ownUpcoming` waits on `Promise.all([fetchMyTickets(), serverTodayKey()])`.
- On a flaky mobile connection where the HEAD (redirect, then SSR) stalls, the Tickets card stays in loading until the browser's own network timeout, even after `fetchMyTickets` has answered.
- Suggested fix: `signal: AbortSignal.timeout(3000)`, which falls through to the existing device-clock `catch`.

The brief also asked about a flash that hides tonight's ticket while loading:

- **MyTicketsPage:** renders with the device key first and then the server key (`serverToday.ts:42-49`, `MyTicketsPage.tsx:202`). If the device clock is ahead, tonight's ticket can sit briefly in Past until the HEAD answers. In practice that is usually before `fetchMyTickets` answers, so the flash is rare. I accept this, since it is the design the brief describes.
- **Ticket card:** waits for both answers, so it has no flash (but see N2).

I accept the cache-once-per-load design (`serverToday.ts:20-34`). The cached promise never rejects, because the `catch` maps errors to the device key.

### (2) useTicketCard: foreign or unreadable `?o=`

The behaviour is correct (`useTicketCard.ts:76-89`):

- An order the account cannot read (`kind: 'error'`) falls back to the person's own upcoming tickets.
- With nothing to fall back to, it still shows `qr_error`.
- `signed_out` still gives `paid_email`.
- With no order id, the old mapping is kept (`signed_out` gives `none`, an error gives `qr_error`).
- `live` is re-checked after the second await.

**N3 (nit): a transient error and a foreign order now look the same** (`useTicketCard.ts:86-88`).

- A real network error on the person's OWN just-paid order also falls back to their other upcoming tickets, with no sign or retry for that order.
- This is usually harmless, because `fetchMyTickets` includes the new order once it is issued.
- Worth a comment, or a check that the fallback list contains `orderId`.

**N4 (nit, test strength): two tests are weaker than their names** (`ticketCardFallback.test.tsx:56-60` and `ticketCardFallback.test.tsx:62-73`).

- "a foreign order id and no tickets of their own still says error" only checks that no QR is shown. It should assert the `qr_error` copy or testid.
- "tonight's ticket stays upcoming when the device clock is behind the server" never moves the device clock, so it passes on the old code.
- "a ticket dated before the SERVER today is not shown" fails on the old code only because the real date at review time is 2026-11-18. From 2026-11-19 it would pass on the old code too.
- Suggested fix: pin the device clock with `vi.setSystemTime` to a day different from the mocked server key in both R2-N1 tests.

### (3) TicketPickerB1 `notYouErr`

The behaviour is correct:

- The error clears whenever `knownEmail` changes (`TicketPickerB1.tsx:84`).
- It is cleared again at the start of each attempt (`:172`).
- It renders only with a known email (`:309`). Given the effect, that render guard is belt-and-braces, but harmless.
- The test covers sign-out elsewhere and then a different address.

### (4) Tests fail on the old code

Yes, for R2-N2 (foreign `?o=`) and R2-N3. R2-N1 fails on the old code only on 18 Nov 2026 (see N4). The handover is honest that missing or malformed `?o=` already worked, so those cases are regression pins, not reproductions.
