## Findings (most severe first)

### 1. The unfinished new organiser's end-of-onboarding button loses its label with P3 live -- fix before arc end -- CONFIRMED

`src/lib/accountRouting.ts:269-275` (`onboardingEndLabel`), read by
`src/modules/dancer-app/screens/onboarding/OnboardingScreen.tsx:48-49`.

With P3 live, `profileSides` sends a new organiser whose dancer profile is unfinished to
`/app/welcome?returnTo=%2Faccount%2Fp3%2Fstart` (`accountRouting.ts:359`, new in this PR). The
end-of-onboarding button names its destination through `onboardingEndLabel(end)`, which knows
`/account/o*` ("Next: set up your organiser page") and `/invite*` ("Next: join the team") but
not `/account/p3/start`, so it falls through to the generic "Continue".

Failing input: `onboardingEndLabel('/account/p3/start')` returns `'Continue'`;
`onboardingEndLabel('/account/o')` returns `'Next: set up your organiser page'`. On `main` the
same person, same flags, saw the specific label. The PR says "every other kind of person lands
exactly where they did before" -- this IS the routed person, and the label regressed. The new
table (`newOrganiserLanding.test.ts`) asserts paths only, never the label, so the matrix did not
see it. Fix: teach `onboardingEndLabel` the P3 start path (one more `startsWith`), with a row in
the table. Flag is OFF in prod, so nobody sees it today.

### 2. "No dancer-profile gate on /account/p3/start" is wrong; the gate exists and drops to the homepage -- nit (doc accuracy; behaviour gap is latent) -- CONFIRMED

Handover and PR body, "Not verified": "`/account/p3/start` has no dancer-profile gate (R1's
`/account/o` has one)".

`src/modules/organiser/p3/shell/P3Routes.tsx:47` wraps every P3 route in `AuthGuard`, and
`src/components/auth/AuthGuard.tsx:95-99` sends a signed-in person whose dancer row lacks
name + city to `/` with no message. R1's gate (`src/components/account/DancerProfileGate.tsx:32`)
sends the same person to `/finish-profile?returnTo=...`. So the difference is not "gate vs no
gate" but "finish-profile with a way back vs silent homepage".

Reachability from this PR's two landings: none in practice. `AuthCallback.routeOnwards` runs only
after `inferOnboardingStatusFromDancer(dancer) === 'completed'` or a successful basics save
(`AuthCallback.tsx:320-375`), and `signInLanding` sends an `'incomplete'` dancer through
`/app/welcome` first. Prod count: 9 organiser-intent accounts with no membership, all 9 have
first name + city, 0 without a dancer row. Correct the sentence in the handover; no code change
needed for this PR.

### 3. Rows missing from the table-driven test -- nit -- CONFIRMED

`src/lib/__tests__/newOrganiserLanding.test.ts:41-50` (KINDS). The brief asked for "every kind x
flag". Kinds the table never sets (all behave as on `main`, verified by reading `signInLanding`
and `profileSides`; none is a regression):

- `areaAllowed: false` with organiser intent, dancer done: still goes to `newOrganiserTo`
  (the `unclaimedOrganiser` branch does not read the gate), so a gate-closed new organiser
  lands in P3 while a gate-closed dancer lands on `/account/dancer`. Worth a row because it is
  the one shape where P3 is reached with the dancer area closed.
- `areaAllowed: false` with organiser intent, dancer `'incomplete'`: `dancerSidePath` gives
  `/account/dancer` and the organiser intent is dropped (same as `main`).
- organiser intent with `dancer: 'no_profile'` (sides = 0): `/app/welcome` with NO
  `returnTo`, so the intent is lost and onboarding ends on `/app/home` (same as `main`; prod
  count 0 today).
- `openRequestCount: null` (failed read) -> `/app/home`; `undefined` -> `{ kind: 'wait' }`.
- `deletion` set -> restore path before any of this.

### 4. Red-first arithmetic does not match the committed file -- nit -- CONFIRMED

PR body: "on the unchanged code exactly the 4 new-organiser x 'P3 live' rows failed (45 passed)".
The committed `newOrganiserLanding.test.ts` has 55 tests (ran it: 55 passed on the branch);
4 + 45 = 49. Also, against unchanged code the file cannot import (`newOrganiserLanding` and
`P3_START_PATH` do not exist on `main`), so the red run used some other harness or an earlier
file. The claim is not reproducible from the PR as committed. The 4 rows named are the right
ones (two `signInLanding` rows, two `landingPathAfterAuth` rows).

### 5. "Only the network edge is mocked" overstates the wiring test -- nit -- CONFIRMED

`src/components/account/profiles/__tests__/newOrganiserWiring.test.tsx:20-46` also mocks
`useAuth`, `useDancerArea` (a gate, not a network edge), `AuthGuard` and `useNoindexMeta`. The
real `useProfileSides` -> `profileSides` -> `signInLanding` chain IS exercised, so the test is
useful; the sentence is just too strong.

### 6. The Welcome's Back arrow leads to a second "Welcome" screen -- nit (pre-existing P3 behaviour, newly first-seen) -- PLAUSIBLE

Traced, not run in a browser. The landing's on-screen Back is `ObShell`'s own
(`OnboardingFlow.tsx:128,169`: `exit` = `navigate('/account/p3')`), not browser history. P3
Home with no page then does `<Navigate to="/account/p3/you/add" replace>`
(`screens/HomeScreen.tsx:50-56`), and `AddPageScreen` titles itself "Welcome" on a first run
(`you/AddPageScreen.tsx:39`). So: Welcome (start) -> Back -> Welcome (you/add), and browser
Back from there returns to `/start`. Not stuck, not a loop, but two Welcomes one tap apart.
The handover's Not-verified line ("Back goes to whatever was before sign-in") describes browser
history, not the arrow that is on screen. Audit L7 noted the inverse hop before this PR.

## What was checked and found right

- **Q1 landings.** Every row in the KINDS table and the `landingPathAfterAuth` ROWS matches a
  hand trace of `signInLanding` / `profileSides` / `landingPathAfterAuth`. Two organisers ->
  `choose`, flag on or off. Existing organiser with intent -> `/account/o` (the organiser side
  wins; `unclaimedOrganiser` needs the single side to be the dancer). Intent + open request ->
  `/app/home` (unchanged; the pending request is not mentioned there -- pre-existing).
  `/invite/<token>`: `signInLanding` returns `returnTo` right after the deletion check
  (`accountRouting.ts:387`); in `AuthCallback` an organiser sign-up honours it because `/invite`
  is in `TASK_PATHS` (`auth-otp-routing.ts:86-100`). The P3 branch is never reached with a
  returnTo. Note `ContinueAsPage` always passes `returnTo = null`; the callback has already
  landed any returnTo before `/account/continue`.
- **Q2 flag OFF.** `organiserP3` defaults to `false` in `landingPathAfterAuth`;
  `newOrganiserLanding(false)` is the same `"/account/o"` literal the function returned before;
  `newOrganiserTo` absent falls to `ORGANISER_HOME_PATH`; `ContinueAs` with `p3Live={false}`
  passes `"/account/o"`, which equals `ORGANISER_HOME_PATH`. 418 tests across the six
  neighbouring suites pass on the branch (`accountRouting`, `accountSidesRouting`,
  `auth-otp-routing`, `DancerFirstGate.matrix`, plus the two new files). The `/account/continue`
  route is not flag-gated (audit L8), so with self-serve OFF and P3 ON `p3Live` is false and the
  landing is `/account/o` -> `/`, as today.
- **Q3 stuck / bounced.** Landing -> `AuthGuard` (session, basics) -> `OnboardingFlow` ->
  `useP3Home` (same query key as `useProfileSides`, so already cached from `/account/continue`)
  -> arrival `'no-page'` -> Welcome step. Refresh: same. Second sign-in with still no page and no
  request: same landing again. `home.isError` shows "We couldn't load your page. Try again." with
  a retry. Nothing strands the person.
- **Q4 source of truth.** `organiser_home_v1` on prod: `entity_members WHERE user_id = auth.uid()
  AND entity_type = 'organiser' AND member_role IN ('owner','manager')`, as the handover says.
  `useProfileSides` and `useP3Home` both use `organiserHomeQueryKey` / `fetchOrganiserHome`. The
  only restated literal is `R1_ORGANISER_HOME_PATH = "/account/o"` in `auth-otp-routing.ts:162`,
  pinned to `ORGANISER_HOME_PATH` by test. The sign-UP branch decides on role metadata alone,
  but `claimOrganisersAtSignIn` / `claimLanding` run first and the Welcome itself re-reads the
  RPC on arrival (`has-page` when a membership exists). No second copy of the rule found;
  `DancerHome.tsx:298-321` links existing organisers (membership present) to `/account/o`,
  which is correct.
- **Q5 shapes.** Re-counted read-only on 2026-10-30: 43 accounts (42 at the survey), 12 with a
  membership, 9 organiser-intent with none (8 then), 6 intent with a membership, 22 dancer-intent
  with none. Consistent with the PR; one account joined since.
