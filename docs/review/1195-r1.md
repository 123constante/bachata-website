# Review r1: Website PR #1195 (new organisers land on P3 Welcome)

Branch reviewed: `claude/p3-landing-welcome` at `1b9021f5` (base `main` `80be3d1`). Read-only review: no src edits, no prod writes.

## Verdict: FIX FIRST

One blocking finding (F1): P3's own Home still sends a person with no page to the old onboarding (`/account/p3/you/add`, which renders R1's `OnboardingView` with the "Signed in > Your organiser > Your events" stepper and the "approved by hand" beta note). That is the owner's symptom 1 ("Back to Home showed the older Find your page") reached by a different door, and the door is the "Go to Home" button on P3's own "Asked to join" screen. A failing test proving it is below.

## Findings (most severe first)

### F1 (blocking): P3 Home with 0 pages goes to `/you/add`, not the rebuilt Welcome
- `src/modules/organiser/p3/screens/HomeScreen.tsx:56`: `return <Navigate to={P3_PATHS.youAdd} replace />;` when `home.data.organisers.length === 0`.
- `src/modules/organiser/p3/you/AddPageScreen.tsx` with `firstRun` true renders `OnboardingView` (`src/modules/organiser/home/onboarding/OnboardingView.tsx:131-140` stepper, `:154` `BETA_NOTE`), titled "Welcome".
- How a person gets there with P3 live:
  1. P3 Welcome > Find your page > Ask to join > "Asked to join X" > **Go to Home** (`OnboardingFlow.tsx:295`, `exit` = `navigate(P3_PATHS.home)` at `:130`) > `/account/p3` > `/account/p3/you/add`. This is the most common path for exactly the person this PR is for (no page, open request).
  2. Any unknown `/account/p3/*` URL (`P3Routes.tsx:86` falls back to `P3_PATHS.home`).
  3. Typing or bookmarking `/account/p3`.
- On that screen the "Waiting for an answer" card is R1's (`OnboardingView.tsx:226`), and R1's `OrganiserSheet.tsx:103` still shows `request_already_open` as an error (red) when the list has not caught up: the already-asked fix in this PR does not cover it.
- Suggested fix: when the home read says 0 pages and the person did not arrive from You > Add a page, send them to `P3_PATHS.start` (e.g. reuse `organiserHomeHandoff(true, 0)` or `newOrganiserLanding(true)`). You > Add a page (a person WITH pages) keeps `/you/add`.
- Failing test (run against `1b9021f5`: **fails** with `expected '/account/p3/you/add' to be '/account/p3/start'`):

### F3 (low): a brief flash of R1's dark shell before the hand-off
`src/modules/organiser/home/index.tsx:118-120`: the hand-off fires only once `home.data` is in (correct: no redirect before the read, none on failure, no loop). Until then R1 Home renders its own loading frame (dark `OrganiserShell` + skeleton), so a cold load of `/account/o` with P3 live shows the old frame for the length of the home read before swapping to P3 Welcome. Warm cache (coming from `/account/continue`, which reads the same `organiserHomeQueryKey`) skips it. Not verified in a browser; worth checking on the walk. A failed read stays on R1's error card (dark) with Try again: acceptable per the code comment, but it is the old look.

### F4 (low): P3's ask does not refresh the requests list
`OnboardingFlow.tsx:211-213` `invalidate` uses `PAGE_STALE_KEYS` (`pageApi.ts:131`: `organiser-home`, `p3-ob-status`, `p3-ob-page`), which does not include `myAccessRequestsQueryKey` (`['my-access-requests', uid]`). After asking inside P3, the new `requests` query (`OnboardingFlow.tsx:397`) keeps its old answer until it refetches by itself. Browser Back to the Find step then shows the page without "Waiting for an answer" and with a live Ask to join; a second tap is caught by the `request_already_open` fallback (`OnboardingFlow.tsx:805`), so no red error, but the row is briefly wrong. Fix: invalidate `myAccessRequestsQueryKey(uid)` in `onAsked`.

### F5 (note): sign-in for a finished dancer with no page now waits on the requests read while P3 is live
`auth-otp-routing.ts:181-182`: `waiting` does not require organiser intent, so every finished dancer with 0 pages waits for `openRequestCount` before leaving `/account/continue` (before: only organiser-intent accounts waited). `useProfileSides.ts:40` always runs that read when signed in, so it cannot hang, and a failed read (`null`) falls through to the old landing. Costs one request's latency for plain dancers. Fine; mention only.
