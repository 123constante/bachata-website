### F3 &mdash; Name-matched fallback can point the Welcome link at a different organiser &mdash; fix before merge &mdash; PLAUSIBLE
`src/modules/admin-organisers/join/JoinPage.tsx:349` &mdash; when `redeemedOrgId` is null the id comes from
`ownPageForName(ownList.data?.organisers, info.organiserName)` (`inviteModel.ts:164`, case-insensitive
trimmed NAME match). Reached when:
- `member === true` (:83) &mdash; the pre-tap name match itself sends the step to `done` (`joinModel.ts:106`)
  without any redeem, so `redeemedOrgId` is null and the fallback is always used; or
- the server returns `done` with `organiser_id` null (`joinModel.ts:229`, `str()` can yield null).

Concrete failing input: person already owns organiser **A "Salsa Co"** and opens an invite to a different
organiser **B "salsa co "**. `member` is true by name, the Done screen says "You're on Salsa Co's team"
and the button now links to `/account/o/welcome?o=<A.id>` &mdash; a Welcome for the WRONG organiser, and the
invite to B is never redeemed. The "never redeemed" half is pre-existing on main (membership-by-name);
this PR adds the wrong-id link on top of it. Renamed organiser: the name no longer matches, fallback is
null, link is plain `/account/o` &mdash; safe, just no Welcome.
Also: `ownList` is disabled once `redeemed` (:76) and therefore holds the pre-join list; with a null server
id the fallback reads that stale list. Not a dead end (Welcome redirects to home when `o` is not among the
person's organisers, `switch/Welcome.tsx:30`), but the id is not trustworthy. Suggest: only use the fallback
when exactly one owned organiser matches the name, or drop it and accept plain home; PLAUSIBLE because
I could not survey prod for duplicate organiser names (see Not reviewed).

organiserP3 x organiserSelfServe x id present/absent, and each expectation matches
`acceptedInviteLanding` (`p3/shell/paths.ts:51`): P3 Welcome only when both flags on, legacy Welcome when

came from (redeem response vs name fallback vs server null; see F2). Also `isRoutable(href.split('?')[0])`
drops the query, so a malformed `?o=` would still pass.
