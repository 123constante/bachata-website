## Findings
1. **[Slice 3, test gap] The real `handleRequest` wiring is untested; five mutants survive.**
   `app/entry.server.tsx:118-124` (`let edge404`, `edge404 = gated.edge404`) and `:174` (`{ edge404 }`).
   `app/catchallGate.test.ts` `catchallDocument()` re-implements the entry.server glue by hand, so deleting or
   inverting the real glue is invisible. `tests/seoSoft404Matrix.test.ts` only reads the status (`gateCatchallDocument`).
   Surviving mutants (all `SURVIVED`, 121/121 green):
   - E1 `edge404 = true` for any 404 (would edge-cache the city-lookup 404, which depends on a DB read)
   - E2 `finalizeDocumentCacheHeaders(..., {})` (feature silently off; no test notices)
   - E3 delete `edge404 = gated.edge404`
   - E4 `edge404 = true` for 503 too (harmless only because `finalize` also requires status 404: defence in depth is the only thing left)
   - E5 `gateCatchallOutcome` returns `{status}` without `edge404`
   Fix: one test that calls `gateCatchallOutcome` / `handleRequest` with a catchall router context for `/zz-probe`,
   `/city/zz-x/parties`, `/zz-x-qq` and asserts the final header. Not a product bug today.
2. **[Slice 1, staleness, proven] A title/date/venue edit with an unchanged cover is stale for up to a year at any shared cache.**
   Proof: scratch test (appendix; not committed) calls the real `loader` twice with the same URL
   `kind=event&id=e1&v=cover.jpg`, facts changed between calls: bodies differ, ETag identical,
   `Vercel-CDN-Cache-Control: ...s-maxage=31536000...` identical -> PASS. The cache key is the URL;
   `v=` is `coverVersionToken` (`app/detailLoader.ts:283`, file name only); `ogFactsTag` enters only the ETag and
   only when `OG_BRANDED_CARD_ENABLED` (`app/lib/ogCardRender.ts:576`), never the URL. `api/og/` is excluded from
   the HTML cache tag so no purge reaches it (ops doc line 108 agrees).
   This is **not new**: `CACHE_OK` already had `s-maxage=31536000` (`api.og.card.tsx:104`) and Vercel honours it.
   The PR's new header changes nothing at Vercel; it matters only when Cloudflare caches the route.
   Cloudflare (owner step 1) makes it worse: Vercel's cache is bounded by the next deploy, Cloudflare's is bounded
   only by its Edge TTL. Ops doc recommends a 7 day cap; **that cap must be a hard precondition, not a recommendation.**
   Safe to merge as is: yes (no behaviour change at Vercel; the CF rule is a separate owner action). Before the CF
   rule: either cap Edge TTL at <= 1 day, or add the facts hash to the URL (`v=<cover>.<ogFactsTag>`; the loader
   in `detailLoader.ts:329-333` and the bake in `ogBakePolicy.ts` both build it), which removes the staleness class.
3. **[Slice 1, unverified] `Cache-Control` the client sees** may now be the full `s-maxage=31536000` rather than today's
   `max-age=86400` once the CDN directive exists (PR's own open item). Not provable here. Check after deploy.
4. **[Slice 3, 5 min window] A page that becomes valid after a 404 was cached is not at risk.** The `unknown` verdict
   is `classifyCatchallPath`: a pure function of the pathname and the build's `CATCHALL_CLIENT_PATHS`. New events,
   organisers, dancers, djs, venues etc. live under real framework routes (`event/:id`, `organisers/:id`, ... in
   `app/routes.ts`) which outrank `*`, so their 404s are loader 404s, which never get `edge404` (proved by row
   "loader-thrown 404" and mutants G2/D3). The only way an `unknown` path becomes valid is a code change, i.e. a deploy,
   and Vercel's CDN cache does not outlive a deploy for these responses (stated by the PR; **not verified here**).
   Worst case 300 s (`EDGE_404`). Acceptable. No tag is set so no purge exists or is needed; a new page is never
   blocked by a tag. Cloudflare applies its own 5 min human-HTML rule to the same 404 (ops doc line 72): same window.
5. **[Slice 3, invariants proven by mutants]** CDN header only for `unknown`: G1 (set false) killed, G2 (city-404 true)
   killed, D2 (`>=400`) killed, D3 (drop `=== true`) killed 10 tests. Never `Set-Cookie`: D7 killed 12 tests (and the
   `skew ON` half of every row). Never a tag: row-level `tag: null` + D1-D3. 5xx / 503: rows "503", "500 thrown by a
   loader", "render error after TAGGED loader", "unknown 404 whose render then fails (500)". Query string: Vercel keys
   on the full URL (ops doc measured `?x=<random>` = fresh MISS), so a scanner's unique query defeats the cache; benign.
   Cookie / Authorization: the 404 body is the same static shell for everyone; Vercel does not store Set-Cookie
   responses and the skew cookie is withheld on this path (D7). No user-specific data in an `unknown` 404. Cookie/
   Authorization request headers are not read by `entry.server` at all.
6. **[Slice 3, weakness in a rule]** `EDGE_404` has `no stale-while-revalidate`; mutant D5 (add SWR) is killed, so it is pinned.
