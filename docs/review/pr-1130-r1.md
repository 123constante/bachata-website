## Verdict: FIX FIRST

The shell and the screens are a faithful port of the approved prototype and the owner's three
changes; the RPC argument shapes match the live function signatures; the matrix and geometry tests
fail when the behaviour they guard breaks (five mutations, all caught). Three things need a fix
before merge, none of them a redesign: one real-data read gap (levels never prefill, because the
prod read RPC does not return `levels_taught`), the PR body's "Verified on real data" section is in
a shape the CI parser rejects, and the on-screen nationality six is not the prototype's six. The
bundle evidence in the handover is vacuous (flag off = no P3 code at all); re-measured with the
flags on below.

### Should-fix (before merge)

**S1. Levels never prefill: the prod read has no `levels_taught`.** `personModel.ts:146` reads
`t.levels_taught` from `my_role_details_v1('teacher').details`, but on prod `_role_details_v1`
(the body `my_role_details_v1` returns) builds the teacher object from `years_teaching`,
`teaching_styles`, `offers_private`, `private_lesson_types`, `private_lesson_locations`,
`private_travel_distance`, `partner_role` only. So `held.levels` is always `[]`: a teacher who saved
levels and comes back sees the Levels screen empty and blocked ("Pick at least one level") and must
answer again; "every screen pre-fills held values" (plan Appendix A) and the handover's read table
("levels, styles, years <- my_role_details_v1('teacher')") are wrong for levels. No test catches it
because both fixtures give the read a key prod does not send: `walk-p3-w4b2-person.spec.ts:26`
(`levels_taught: ['Beginner']`) and `personModel.matrix.test.ts:131-134`. The write side is fine
(`save_my_role_v1` S1LV block parses, validates and diffs `levels_taught`). No one is hit today
(`levels_taught` is null on all 21 teacher rows), so this is a returning-user bug, not a launch
blocker, but it is exactly the real-shape class CLAUDE.md's definition of done exists for.
Fix: the read is admin-repo work (`_role_details_v1` to emit `levels_taught`, with a Website
contract check pinning the key); until it lands, the handover and the PR body must say levels are
not prefilled, and the two fixtures should drop the key they invent (or the matrix should carry a
"prod today" shape without it).

**S2. The PR body fails the `real-data-verified` gate.** The section exists, but the three labelled
lines are bold labels with the content in sub-bullets. `PR_BODY=... node
scripts/check-pr-real-data-verified.mjs` on that section returns: "Shapes surveyed: line is
missing; Checks run: empty after the colon; NOT verified: empty after the colon". The parser wants
`- Shapes surveyed: <text>`, `- Checks run: <text>`, `- NOT verified: <text>` each on one line, no
bold. Reformat the body (content can stay the same).

**S3. The on-screen nationality six is not the prototype's six.** Prototype `NAT_FEW = ['GB', 'ES',
'DO', 'IT', 'PL', 'BR']`. The PR passes `POPULAR` as the "few" list (`PersonFlow.tsx:409`), and
`sixFor` takes `few.slice(0, 6)` (`personModel.ts:80`), so the chips are United Kingdom, England,
Scotland, Wales, Northern Ireland, Spain (`personModel.ts:58-62`). Owner change 3 asked for
home-nation FLAGS, not for the home nations to displace Dominican Republic, Italy, Poland and
Brazil from the first screen. Fix: a `NAT_FEW` list equal to the prototype's for the chips; keep
`POPULAR` as the sheet's first section (`CountryRows`, `PersonFlow.tsx:450`).

**S4. The bundle claim rests on a flag-off build, which proves nothing; re-measured with the flags on.**
`organiserP3` is build-time (`src/lib/featureFlags.ts:67`: `import.meta.env.VITE_ENABLE_ORGANISER_P3 === 'true'`)
and `AnimatedRoutes.tsx:264` mounts the P3 area only when it is on, so a flag-off build contains no
P3 code at all: the PR's own `build/client/assets` has no chunk containing "Save it privately", and
"every route byte-identical" is true by construction. With BOTH flags on (the state the owner's
walk and the Vercel preview with the flag need), on `origin/main` and on the branch:
| Build | /app first-load JS | chunks | Note |
|---|---|---|---|
| `origin/main`, flags on | 375.3 KB | 50 | already over the 374 KB budget: the budget and the 49-chunk ratchet are tuned to the flag-off build |
| branch, flags on | 375.6 KB | 51 | **+0.3 KB and +1 request on /app's first load** |

The extra request is `assets/countries-*.js` (0.5 KB). `PersonFlow.tsx:7` imports
`@/constants/countries` statically and the dancer app already does, so Rollup splits the shared
module out of `dancer-app` (31.7 -> 31.4 KB) into a chunk that /app's first load now fetches: the
"one more request" pattern CLAUDE.md's chunk notes warn about. The `PersonFlow` chunk itself
(29.4 KB) and `world-countries` stay lazy and are not in the list. Fix: load the module inside
`useCountries` with `import('@/constants/countries')` (or move `POPULAR` out of the static graph), so
it stays in `dancer-app` for /app and in the route's own chunk here; then re-measure with BOTH flags
on, on main and the branch, and put those two numbers in the PR body instead of the flag-off ones.

**S5. The `dancer_area_open` dependency is real; document it and name the failure.** Confirmed on
prod: `app_feature_flags.dancer_area_open` enabled = true (since 2026-10-15); `_dancer_area_allowed_v1`
is "flag on OR confirmed email on `dancer_area_access`". If the flag is ever turned off, `my_dancer_edit_v1`
raises `area_closed` for everyone not on that list and the whole flow shows the generic "We couldn't
load your details" (`PersonFlow.tsx:68-76`), with Retry doing nothing. Low likelihood, total impact.
Fix: a line in `docs/plans/onboarding-arc.md` risks (organiser onboarding now shares the dancer
area's gate) and, cheaply, map `area_closed` to a message that says what happened.

**S6. The percentage is relative to the 11 person steps, not the whole onboarding path (slice 3 must rebase).**
`progressPercent(step, personPath(...))` (`personModel.ts:26-30`) reaches 100% on Personal email,
while the prototype's bar counts 17-18 groups across the whole path (contact, WhatsApp, category,
link, logo, then the person screens, then Review). Correct for this slice in isolation; slice 3 has
to pass the full path in (or the bar will read 100% with Review still ahead). Record it in the
slice 3 brief.

### Nits

**N1. The toast timer restarts on every render.** `ObShell.tsx:108-111` keys the timeout on
`onDone`, and `PersonFlow.tsx:302` passes a new arrow function each render, so typing while the
toast shows keeps it alive. Memoise `onDone` or drop it from the deps.

**N2. "Save it privately" celebrates a no-op.** `save_my_signin_email_v1` returns
`{ok, changed: false}` when the private copy already matches or when `show_contact_publicly` is on
(nothing is written then, by design). `personApi.ts:339` discards `changed`, so the bounce and
"saved" feel the same either way. Fine for slice 1; worth a different label if the owner keeps the
screen (see Decision 1).

**N3. `?o=` is not checked against the person's own pages.** `PersonFlow.tsx:56` takes any id; a
live organiser the person does not manage shows "About <name>" prefilled with its public bio
(RLS: live rows are readable by anyone; verified) and the save fails `permission_denied`, shown as
the generic "Couldn't save". No leak, but scope `?o=` to `home.data.organisers` ids when slice 3
adds the link.

**N4. Stale keys after an About save.** `PERSON_STALE_KEYS` (`personApi.ts:346`) names the dancer
keys only; the P3 home / organiser queries keep the old bio until their 30 s staleTime passes.

**N5. The geometry walk measures the filled persona only.** `walk-p3-w4b2-person.spec.ts:67` is
`for (const filled of [true])`; the empty persona (helper line + reason line under the button, the
tallest state on name / photo / years) is measured on the name screen only (`:94`). The loop is
already shaped for `[true, false]`.

**N6. Esc is swallowed globally.** `ObShell.tsx:31-35` calls `preventDefault` on every Escape on
`window`, including the native clear of the `type="search"` field. Harmless; the draft is kept.

## 3. Decision 1 (personal email screen)

The two approved documents disagree. The prototype's screen 20 (`onboarding-prototype.html`,
`data-id="email"`) is a field: "You sign in as sam@example.com. If that is a shared or work inbox,
add a personal one so you never lose the page." The plan (`onboarding-arc.md` 4.1) defines the only
RPC as `save_my_signin_email_v1()`: "copies `auth.users.email` to the caller's PRIVATE
`dancer_profiles.email`", no argument, and that is what is live. The builder followed the live
contract, which is the right call for a Website-only slice. It is acceptable for slice 1 behind the
flag, and it is a product call for the owner, because the screen as built asks the person to tap a
button whose effect they cannot see (and which is a no-op for a public-contact teacher):

- (a) keep the copy semantics: then the screen can go. The copy can run silently at completion
  (slice 3's go-live) and the path loses one step.
- (b) keep the prototype's intent (a different personal address): an admin RPC
  `save_my_personal_email_v1(p_email)` with validation + audit, and screen 20 returns as a field in
  a later slice.

Recommendation: (a) now, (b) only if the owner wants the "shared or work inbox" case solved.
