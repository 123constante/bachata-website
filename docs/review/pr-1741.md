## Brief question 1: every v3 refusal maps to a refusal, unknown defaults to refuse -- CONFIRMED

Server side (live `_ticket_check_in_core_v3` and `_ticket_door_refusal_v1`), the complete set of
`result` values a check-in can carry is: `ok`, `already_in`, `unknown_code`, `wrong_event`,
`refunded`, `void`, `not_valid`, `wrong_night`, `wrong_day`, `add_on_not_admission`,
`unclassified_festival_type`, plus `not_allowed` and `too_many_attempts` from the wrappers.

Client side, `parseCheckIn` (`data.ts:35-36`) is a whitelist: a value in `RESULTS` (`data.ts:24-25`)
keeps its name; `refunded` / `void` (`data.ts:27`) become `not_valid`; anything else, including a
missing `result` key (`String(undefined)` is `'undefined'`), becomes `unknown_code`. The screen chooses
the band only through `RESULT_TABLE[c.result]` (`DoorScreen.tsx:306,313`), and the only row with
`band: 'ok'` / headline LET IN is `ok` (`model.ts:78`). The four new rows (`model.ts:125-148`) are all
`band: 'bad'` with "Do not let in" in the detail. `already_in` stays `warn`. So the mapping is:

| server value | shown as | band |
|---|---|---|
| ok | LET IN | ok |
| already_in | ALREADY IN | warn |
| wrong_event | NOT FOR THIS EVENT | bad |
| refunded, void, not_valid | NOT VALID | bad |
| wrong_night | WRONG NIGHT | bad |
| wrong_day | WRONG DAY | bad |
| add_on_not_admission | NOT AN ENTRY TICKET | bad |
| unclassified_festival_type | CANNOT CHECK THIS TICKET | bad |
| unknown_code, anything unknown, no result key | CODE NOT RECOGNISED | bad |
| not_allowed | CANNOT CHECK TICKETS | grey |
| too_many_attempts | TOO MANY WRONG CODES | warn |

`door.v3.matrix.test.tsx` covers each of these through the real `data.ts` (only `supabase.rpc` is
faked) and asserts both `data-state` and that no `.p3-door-band-ok` is rendered. Checked on the PR
head: 429/429 pass.

## Findings (most severe first)

### 1. On a series whose every night has ended, a scanned ticket reads "for a different night" -- nit, CONFIRMED
- Where: live `ticket_check_in_v3` (and by_code / by_id) answer `wrong_night` from the
  `NOT EXISTS (... n.id = p_occurrence_id ...)` guard when the NULL branch found no night left,
  before any ticket is looked up. The client shows the `wrong_night` row (`model.ts:125-130`):
  sub "This ticket is for a different night", detail "Their ticket is for another night of this event."
- Failing input: a weekly series whose last night ended an hour ago; a staff member scans any ticket.
  The card is a refusal (correct) but tells them the ticket is for another night, when the truth is
  that no night is on. The Tonight's list tab gets this right ("No night of this event is on now",
  `DoorScreen.tsx:458-461`), so the two tabs disagree.
- Door-safety effect: none; still a bad band, still "Do not let in".
- Possible fix (follow-up, not in this PR): when `list.data?.result === 'wrong_night'`, show the
  no-night card in the Scan tab too (or swap the result card's words), so staff are told the event is
  over rather than hunting for the right night.

### 2. `p_occurrence_id` is typed `string`, not `string | null`, and only a cast lets `null` compile -- nit, CONFIRMED
- Where: `src/integrations/supabase/types.ts:17680,17699,17719,17815` say `p_occurrence_id: string`
  (the generator cannot express Postgres parameter nullability). `data.ts:14` casts the client to
  `{ rpc(fn: string, args: Record<string, unknown>) }`, so `tsc` never sees the arg types; this cast
  predates the PR.
- Effect: the brief's "nullable" is true on the server (verified today by reading the live bodies)
  but is not a compile-time contract. If admin ever drops the NULL branch, nothing here would turn
  red until the door answers `wrong_night` for every scan. The `door.v3.matrix` names+args test pins
  the client side; nothing pins the server side.
- Possible fix (follow-up): a contract check (`scripts/check-*.mjs`) or a comment in `data.ts` naming
  the admin migration that added the NULL branch, so the dependency is grep-able.

### 3. `door_day` / `valid_day` are sent by v3 and parsed by nothing -- note, not a finding
The handover says so honestly. On a festival the list card and result card show nothing about which
day the door is on. Fine for this slice; the day picker is a later slice.
