### F2 -- `src/modules/organiser/shared/publicViewKeys.ts:12` -- series-id narrowing misses the public page of bridged series (59 of 69 live)
**Severity: would block on its own. CONFIRMED (live function body + read-only counts on prod).**

The public event page is keyed `['event-page-snapshot', <id>, occurrenceId|null]` where `<id>` comes
from `resolve_public_event_ref_v1` (`src/lib/seo/resolvePublicEventRef.ts` -> `useEventPage` ->
`useEventPageQuery`). The live function returns `'id', COALESCE(r.legacy_event_id, r.id)`: for a
bridged series the public page key holds the LEGACY event id, not the P5 series id this PR passes.
`publicEventPageKey(seriesId)` = `['event-page-snapshot', seriesId]` then matches nothing.

Prod, read-only, 1 Nov 2026 (`event_series_p5`, `legacy_event_id IS NOT NULL AND <> id`):

| lifecycle | series | bridged (public id differs) |
|---|---|---|
| live | 69 | 59 |
| ended | 21 | 21 |
| paused | 2 | 1 |
| draft | 13 | 0 |

Failing scenario: the organiser of any of those 59 live series cancels a date in `/account/p3`,
then opens the event page in the same tab. The `event-page-snapshot` entry (staleTime 1 h) is not
marked stale, so the cancelled date still shows -- the exact A-public-7 symptom F-33 exists to fix.
The calendar half is fine (`['calendar-events']` root prefix).

The new test cannot see this: `publicViews.invalidate.test.tsx` seeds `eventPageQueryKey(SID, ...)`
with SID = the P5 series id, which is the one shape prod mostly does not have. Main's #1220
invalidates by root for exactly this reason (comment in `publicCache.ts`: "not the P5 series id for
most series (81 of 92 on prod, 2026-10-31), and the workspace carries no legacy id").

### F3 -- `runCommands.ts:52-58`, `dates.ts:418-425`, `useOwnerCommand.ts:64-66` -- a refused or failed save still invalidates
**Severity: contract question, not a defect I would block on. CONFIRMED (test pins it).**

The brief's check 2 says a refused or failed save must not invalidate. The PR invalidates in
`finally` (useSendOnce, useRunCommands, useSendPlan), on `version_conflict` (useOwnerCommand) and on a
reload-worthy refusal (useDateSend), and the test "a refused save still refreshes them" locks that in.
Two honest notes: (a) marking stale is cheap and only refetches when the public query is next
observed, and after a lost reply the write may have landed, so refreshing is defensible; (b) main's
#1220 does the same in `useReload`. If the brief's rule stands, it is a follow-up on main, not a
reason to prefer this PR.

### F4 -- `dates.ts:150-170` (`useAllDatesWorkspace`) -- design delta against main, for the record
**Severity: informational.**

- Auto-loads every older page as soon as All dates opens (serial RPCs, 200 per page; each page
  carries the full series snapshot + programme tree because the RPC always builds them). Main loads
  on a tap. For prod's one 132-date series this is one extra RPC; neutral.
- Counts while loading / after a failure are "N+" for Past, Cancelled, Breaks and Own even though the
  RPC already returns whole-series `meta.total` and `meta.counts` on the first read (main uses them).
  Breaks is whole from `removed_dates` regardless, so "N+" there is more cautious than needed.
- Past the 10-page cap (2,100 dates) the person sees "N+" counts and the "This page lists the
  newest 2100 of N dates." line, with no way to load more. Acceptable for prod (max 132).
- Paging correctness is sound: `p_before` is strictly-before on `UNIQUE (series_id, occurrence_date)`
  (constraint `event_occurrence_p5_series_id_occurrence_date_key`, confirmed), `next_before` is the
  page's `min(occurrence_date)`, `has_more` is `EXISTS ... OFFSET v_limit` on the same filter. No date
  can be duplicated or skipped across a boundary; the `nextBefore >= cursor` guard stops a stuck cursor.
- I probed one scenario the matrix lacks: a series shrinking from 101 to 100 dates with the same
  oldest date in the read (the older query's key does not change while `hasMore` flips off). The
  stale older page is refetched because the invalidation lands while the query is still enabled; the
  screen showed 100, not a phantom 101. Not a defect; the ordering is implicit rather than guarded.

### F5 -- the two new tests -- non-vacuous, but "red on main" does not mean what the PR body implies
**Severity: nit.**

fail on main because main needs a tap and reads `meta.counts`, which the test's fake RPC never
sends (the live RPC always does). So the fake is not a faithful model of the live function on
that point, and the red-on-main claim does not show main lacks F-27 or F-33.
