# Review r1: PR #1208, P3 create-event slice 1 (new save logic)

Independent review of `claude/p3-create-event-build` at `bb1d867` (main merged in), against the brief
`docs/briefs/review-1208-r1.md`. Reviewer worked on a separate worktree; nothing on the builder branch was
touched. The two in-branch rounds (`5b19f41` round 1, `49045cf` round 2) were read first and are not repeated:
their fixes are confirmed below where this review re-tested them.

## Verdict: PASS WITH NITS

The new save logic holds up: one save at a time, one idempotency key per step for the life of the screen,
readback checks the id, a landed create never hijacks the next New event, the version is read again before a
retry and a discard, and a retry keeps Go live. Each of those is pinned by a test on the branch or was broken
against here without success (section 1). Nothing found is a data-integrity defect. The findings are one
behaviour no test pins (F1), two known FIXLIST items this PR carries but does not declare (F2, F3), a CI gate
that is narrower than it looks (F4), and documentation and route nits.

**F1 (medium, no test pins it): the save keeps running after the person leaves the screen, and moves them
later.** `run()` holds no mounted flag. Reviewer probe T3: Save draft, then (while "Saving" shows) tap a
link to Events. The create lands after the screen is gone; the promise goes on, sends the sessions, and
`navigate(P3_PATHS.event(id))` at `useCreateSave.ts:155` pulls the person from `/account/p3/events` to the new
event page. In the failing variant (a step fails after the screen is gone) `setState` at `:170` lands on an
unmounted screen: nobody is told the draft is incomplete; it only shows under Home "Needs you". Cancel is
disabled while busy (`CreateFlow.tsx:174`) but the browser Back, the tab bar and a deep link are not.
Fix: a `mounted` ref set false in an unmount effect; after it, skip every `navigate`/`setState` in `run`,
`landed` and `discard` (storage already holds `created: true` at `:89`, so the next New event stays safe),
and add the probe as a test (`review3`: leave mid-create, release the reply, assert the URL stays on Events).

Probe tests were run from the reviewer's worktree only (not committed anywhere):
T1 PASS, T2 PASS, T3 FAIL (as described: URL became `/account/p3/events/<id>`).

## 2. Cover upload before the create (FIXLIST F-15)

Confirmed: `uploadEventPicture(seriesId, cover)` runs at `useCreateSave.ts:121-124`, before the create at
`:146`. A refused create (onboarding or any other error) leaves the file in storage under a series id that
has no row. `coverUrl.current` is kept, so a retry does not upload twice, and `forgetCover` (`:203-208`)
lets a new photo replace it (one more stray). What the person sees: the refusal card says "Nothing was
saved; what you typed is still here" (`CreateFlow.tsx:230`) and the generic card says "Nothing was saved"
(`:234`), while the photo IS stored; the preview stays and `coverUploaded` stays true.

Scope: main's `docs/design/p3-acceptance/FIXLIST.md:34` lists F-15 (low, GATE-RETRY batch, fix NO) against
exactly these lines, and `:124` says GATE-RETRY must land before the P3 flag is turned on. So it is correctly
deferred, BUT this PR body does not mention F-15 at all. **F2 (low): add F-15 to the PR body's "Not
verified / known" list, and soften the copy now: "Nothing was saved" is untrue when a photo went up; say
"The event was not saved" (the photo line can stay silent until GATE-RETRY cleans up strays).** A server-side
sweep of cover files whose series id has no row is the real fix and belongs to admin.
