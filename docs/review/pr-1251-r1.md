## Findings (ranked)

### 1. BLOCK: F-24, the router blocker sends FieldSheet into an endless render loop
- **Where:** `src/modules/organiser/p3/screens/DateFieldSheets.tsx:47-49`, together with `EditTray.tsx:167-176` (`useLeave`).
- **Cause:** FieldSheet passes `useLeave` an **inline** callback, so it is a new function on every render. `useLeave`'s effect `[blocker, setAsk]` therefore runs again after every render. While `blocker.state === 'blocked'`, each run calls the callback, which does `setRouteGo(() => a.go)`. `a.go` is a fresh arrow every time, so the state really changes, which triggers another render, another effect run, and so on forever. EditTray avoids this because it passes a stable `useState` setter.
- **Failing input:** open a date, then Name; type one letter; tap any tab-bar link (or phone Back). The browser tab hangs.
- **Proof:** I built a data-router harness (`createMemoryRouter` + `RouterProvider`) with FieldSheet's hook wiring copied verbatim.
  - "Clean sheet, tab tap" passes: no block.
  - "Dirty, tab tap" **hangs vitest until it is killed** (timeout 60s, exit 143), reproduced twice.
  - The same file with the callback wrapped in `useCallback(..., [])` passes all 4 cases in 92ms: clean is not blocked; dirty asks exactly once; Stay resets the blocker and a second tap asks again; Leave proceeds; POP (Back) asks and Stay keeps the page.
- **Suggested fix:** make the callback stable, e.g. `const onAsk = useCallback((a: Ask) => { if (a?.kind === 'leave') { setRouteGo(() => a.go); setAsk('leave'); } }, []);`. Alternatively, make `useLeave` hold `setAsk` in a ref so no caller can loop it. Then add the test below to the PR.
- **Test to add** (the builder's "Left / next" gap). Put it under `p3/screens/__tests__/`, with a data router, against the real `DateFieldSheet` (or the harness below if the fixtures are too heavy):
  ```tsx
  const router = createMemoryRouter([{ path: '/e', element: <Sheet startDirty /> }, { path: '/tab', element: <p/> }], { initialEntries: ['/e'] });
  render(<RouterProvider router={router} />);
  fireEvent.click(screen.getByTestId('tab'));          // blocked
  expect(router.state.location.pathname).toBe('/e');
  expect(screen.getAllByTestId('ask')).toHaveLength(1); // one prompt, no loop
  fireEvent.click(screen.getByTestId('stay'));          // blocker reset
  expect([...router.state.blockers.values()].every(b => b.state === 'unblocked')).toBe(true);
  fireEvent.click(screen.getByTestId('tab')); fireEvent.click(screen.getByTestId('go'));
  expect(router.state.location.pathname).toBe('/tab');
  // + clean sheet: tab tap navigates; + router.navigate(-1) while dirty asks
  ```
  Against the current code this test hangs rather than going red. Run it under `--testTimeout` so a hang reads as a failure.

### 4. LOW (decision for Ricky): F-22, "Removed" on events nobody removed
- **Live shapes** (read-only count, prod `stsdtacfauprzrdebmzg`, `event_series_p5`): 653 archived series. 82 of them carry organisers, and 39 of those came from the legacy import (`legacy_event_id` not null), most likely archived by migration or admin, not by the organiser. Other counts: ended 21, live 69, draft 13, paused 2.
- **Who reads status:** `organiser_home_v1` excludes archived (`lifecycle_status <> 'archived'`, "archived series never reach Home"). So Home, Events, `whenLine` (`data/home.ts:73`) and `groupsOf` (`home.ts:213`) never see the new label. The only surface is the event page reached by URL (`eventPage.ts:131`). The blast radius is therefore small, but an organiser following an old link to a migration-archived event reads "Removed / It was removed" for something they never removed.
- **Suggestion:** accept as is, or use a neutral word ("No longer listed"). Not blocking.
