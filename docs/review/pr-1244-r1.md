# Review: PR #1244 (claude/claim-edit-fix-r1), round 1

Reviewer: read-only review, correctness only. Diff: `git diff origin/main...origin/claude/claim-edit-fix-r1` (head 6f25e57).

## Verdict: BLOCK

Finding 1 can lose photos the organiser believes are saved, and Finding 2 brings back photos after Undo. Both come from one gap: Details does not treat a photo upload in progress as busy, which the date Photos sheet (`DateFieldSheets.tsx:37-71`, `uploading`) already does. Finding 3 is copy that is false for 22 real prod series. Each fix is small.

## Findings (ranked)

### 1. HIGH: Save and Leave are live during a photo upload, so photos are lost or left orphaned
- `src/modules/organiser/p3/screens/DetailsScreen.tsx:190`: `EditTray ... busy={save.busy}` never gets `pics.busy`. `useBackToEvent(ws.series.id, form.dirty)` (line 35) does not know about uploads either.
- Failing input A: pick 3 photos on a slow network. Photo 1 lands, so `set({gallery:[p1]})` runs and the form is dirty. Tap Save. The plan sends `default_gallery` with `[...old, p1]`, then `back(...)` goes to the event page and shows "Saved for every date". p2 and p3 finish uploading into an unmounted form, so they end up in storage, not in the gallery. The organiser thinks 3 photos were saved; only 1 was.
- Failing input B: pick photos, then tap Back before the first one finishes. `form.dirty` is false, so there is no "leave?" question. You leave, and the uploads are orphaned.
- Fix: do what PhotosSheet does. Pass `busy={save.busy || pics.busy}` (or a new `uploading` prop) to EditTray so Save and Undo are off. Make the leave guard ask when `pics.busy || photo.busy`. The cover upload (`photo.busy`) has the same hole, but it was there before this PR.

### 2. HIGH: Undo during an upload brings the removed photos back
- `DetailsScreen.tsx:76-84`: `addPics` builds on `let list = draft.gallery` (taken when the tap happened) and calls `set({ gallery: list })` after each file. Undo (`:191`) also sets `pics` to `busy:false`, which turns "Add photos" back on while the loop is still running.
- Failing input: the gallery has [a,b]. Add 2 files. After the first lands the draft is [a,b,n1]. Tap Undo and the draft goes back to [a,b]. The second file lands, `list = [a,b,n1,n2]` is written, and n1 comes back even though Undo removed it. If the organiser removes `a` and then adds files, and Undo is tapped during the upload, the old list is written back over the reverted draft. After Undo, a second "Add photos" can also run alongside the first loop, and each loop writes its own stale list over the other (photos are dropped).
- Fix: append with the functional form, as PhotosSheet does: `form.setDraft((d) => ({...d, gallery: [...d.gallery, url]}))`. Keep Undo and Add disabled while `pics.busy` (Finding 1). Or give each upload run a token and drop results that arrive after an Undo.

### 3. MEDIUM: "every date" copy is false for series whose dates have their own photos (22 prod series)
- `labels.ts` `detailsPhotosHint: 'Shown on every date’s event page...'` and `detailsSaved: 'Saved for every date.'`. A date with its own photos (`dateGalleryOf` = `detail?.galleryOverride ?? ws.gallery`, `data/dateFields.ts:44`) keeps them, so the new series gallery does not show there.
- Prod (read-only count): 48 per-date photo overrides across **22 series**.
- Failing input: a weekly series where 2 of 16 dates have their own photos. Change Photos on Details. The hint and toast both say every date, but 2 dates still show their old photos.
- Fix: write the hint as "Shown on every date that has no photos of its own", or count the dates with their own photos and say so. At minimum, do not say "every date" when there are overrides. Add a matrix row for "series gallery + 2 dates with their own photos".
- The raw `’` in the label is an escape sequence, not a pasted character, so the mojibake rule is fine.

### 4. LOW: picking more photos than the cap allows drops some without saying so
- `DetailsScreen.tsx:80` `files.slice(0, MAX_GALLERY - list.length)`: with 28 photos, picking 5 uploads 2 and silently drops 3. The only sign is the cap note that appears afterwards. PhotosSheet behaves the same way (it was there before). A gallery already over 30 is not reachable today: prod max is 5, there are 0 series over 30, and the Add button is hidden at 30 or more.
- Fix (optional): if any files are dropped, show `datePhotosMax(MAX_GALLERY)` as the error.

### 5. LOW: the wording for 0 dates claims "all dates"
- `model/saveWords.ts:15`: with `hasOneDate(0, 0)` false, a draft with no dates says "Save for all dates" and "Saved for every date." There are no dates.
- Fix: treat `listed <= 1 && (total ?? listed) <= 1` as the plain "Save" / "Saved." case.

## Checked and OK (brief questions)
1. **Untouched gallery sends nothing.** `DETAILS_SPECS` gallery uses `sameList`, and `detailsPlan` only adds `default_gallery` when it changed (`data/details.ts:172`). The key and form match the older series editor (`events/eventModel.ts:238`), so the server already accepts it. When photos are added or removed, the whole new list is sent: no partial list, and no duplicates from the code (Finding 2 aside). A gallery that is null or empty reads as `[]` (`strings()`); prod has 0 null, 728 empty, 30 with 1-30 photos, max 5. A gallery over 30 only blocks the save when the gallery itself changed (`detailsBlocker` only looks at changed keys), so an untouched legacy gallery over 30 cannot block a name edit.
2. **Per-date overrides** are not touched by the upsert (only the copy problem in Finding 3).
3. **Other fields in the same upsert:** the payload builder is unchanged apart from the one `gallery` line. Cover, ticket and the rest are still conditional on their own change, and the name still rides along. `detailsLandedKeys` covers `gallery` through the spec list, so a 2-step save (upsert + group chat) whose second step fails keeps the gallery as landed.
4. **hasOneDate:** `ws.dates` is the whole page, past and cancelled dates included, and `total` comes from meta. One date: "Save". One date + a cancelled or past date: "Save for all dates" (true: there are 2 dates). `total` null with 1 listed: "Save". Weekly with 16 or 30 dates: "all dates". 0 dates: Finding 5.
5. **EditRows move:** the test ids (`p3-edit-rows`, `p3-open-*`) and routes are unchanged. It is now a sibling before Sessions, so the DOM, tab and focus order follow what you see. No copy points at a control that is not on screen. The `p3-gap-t` spacing class was dropped, which is fine at the new place.
