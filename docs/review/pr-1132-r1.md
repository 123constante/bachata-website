### Should-fix

**S1. The PR body and three code comments say `complete_organiser_onboarding_v1` is NOT deployed on prod. It is.**
`pg_proc` on prod holds `public.complete_organiser_onboarding_v1(p_organiser_id uuid) RETURNS jsonb` (owner-only,
refuses with `incomplete` + missing[], moves draft/rejected to live or pending_review by `_city_requires_review_p5`).
The brief confirms it landed today via admin #1119. The STUB is still the right call for this PR (the brief says do
not wire it), but the words are now wrong and a later slice will act on them:
- `docs/handovers/p3-w4b2-page-prbody.md` "Go live: `complete_organiser_onboarding_v1` is NOT deployed on prod" and
  "`complete_organiser_onboarding_v1` confirmed not deployed" (Verified block).
- `src/modules/organiser/p3/onboarding/pageApi.ts:44-47` ("is NOT deployed on prod (checked 2026-10-29)").
- `src/modules/organiser/p3/onboarding/pageModel.ts:333-334` ("it does NOT on prod 2026-10-29").
- `pageScreens.matrix.test.tsx:308` title "... while the RPC is not deployed".
Fix: say "deployed in admin #1119; intentionally not wired in this PR, `deployed: false` until the go-live slice",
and change the `GO_LIVE_NOT_YET` rationale comment. No behaviour change.

**S2. The progress bar goes backwards by one point while a number is typed on the phone screen.**
`waPhone` is recomputed from the LIVE draft on every keystroke (`OnboardingFlow.tsx:145`
`const waPhone = !!(d && (e164Of(d.phone) ?? phoneE164(d.phone)))`), and `fullPath` adds the WhatsApp group when it
is true (`pageModel.ts:34`). On `contact-phone` the person is in group 1 (or 2), so the denominator grows under them.
Measured with the real functions (10 person steps):

| Path | contact-phone, field empty | contact-phone, valid number typed |
|---|---:|---:|
| has-page, teach yes/null | 7 | 6 |
| no-page, teach yes/null | 13 | 12 |
| no-page, teach no | 15 | 14 |
| has-page, teach no | 8 | 8 |

The brief's rule is "never goes backwards". One point, one screen, but it is the one screen where the person is
looking at the bar while typing. Fix: derive the WhatsApp fact for the % from the HELD phone (or from the draft only
once Continue has run), e.g. pass `waPhone` as a committed fact next to `arrival`, not a derived one. The matrix
test `full-path progress` walks a fixed `waPhone`, so it cannot see this; a test that types into the phone field and
reads `aria-valuenow` before and after would.

**S3. A brand-new person (no dancer profile) hits a server refusal on Create and loses the typed name and city.**
`create_organiser_profile_v1` (prod body) calls `_require_complete_dancer_profile_v1()` first, which raises
`profile_incomplete` unless the caller's dancer profile has first_name, city, dance_role and photo (admins exempt).
The flow asks the page questions BEFORE the person questions (spec order), so the no-page persona who most needs
onboarding is refused at "Create page". The refusal is handled (`OnboardingFlow.tsx:420` maps `next: 'finish_profile'`,
`:498` shows "Finish your profile", `:310` navigates to `finishProfileHref(P3_PATHS.start)`), but the return URL is
the flow's root: `stage` resets to Welcome and `d` to `EMPTY_PAGE`, so the name and city typed are gone. AuthGuard
on `/account/p3` does not gate on profile completeness (no `profile_incomplete` / `finishProfile` reference in
`P3Routes.tsx` or `AuthGuard.tsx`). `claim_organiser_v1` / `request_organiser_access_v1` were not read for the same
rule (the helper's own comment says it guards "any organiser create / claim / access request / invite redeem").
Fix options (owner's call, not this PR's reviewer's): read `organiser_onboarding_status_v1().person.missing` on
Welcome and, when first_name/city/dance_role/photo are missing, run the person screens first for the no-page arrival;
or at least return to `create-name` with the draft kept. Not in the e2e personas (the `none` persona's fakes accept
the create).

**N4. `<section role="status">` wraps two controls** (`GraceBanner.tsx:86-95`). A live region that contains a
Link and a button is read out as a whole on change; the status role belongs on the text, not the card.

**N5. The `screens.matrix.test.tsx` mock of GraceBanner hides Home+banner integration, not the banner.** The mock

`organiserP3` off, P3Routes is not mounted at all (section 5).

**N6. "Yes, that's right" on a legacy number keeps the legacy string; Continue on a pre-filled 07 number writes.**
`pageCommandFor('contact')` sends `confirm` with `p_phone` null (`pageModel.ts:217`), so the 5 legacy rows on prod stay
as stored; `contact-phone` with a held `07...` sends `confirm` with the `+44` form (`:221`), a write on a screen the
person did not edit. Declared as decision 5 in the handover; consistent with the server (it normalises and no-ops an
equal phone). Mentioning it because the brief asks "nothing when untouched".
