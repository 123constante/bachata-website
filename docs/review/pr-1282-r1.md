## Findings (most severe first)

### F1 (Medium) Hero stats strip still shows a false "0" while that feed has failed
`src/pages/OrganiserProfile.tsx:1385-1386`. The strip renders `totalUpcomingDateCount`
and `pastEvents.length` unconditionally. With the future feed failed the page shows the
new error line AND "0 Upcoming dates" above it; with the past feed failed, "0 Past
nights"; with the events feed failed, both zeros. Verified by rendering the page with
the PR's own matrix harness:

| failed feed | Upcoming dates | Past nights | error line |
|---|---|---|---|
| future (upcoming) | 0 | 1 | yes |
| past | 1 | 0 | yes |
| events (join source) | 0 | 0 | both |

This is exactly the claim S1 exists to stop ("a failure is not 'no nights'"), stated as a
number instead of a sentence. Suggested fix: when `upcomingFailed` / `pastFailed`, render
an en-dash (`&ndash;`) or hide that stat, and add a row to the matrix test asserting the
strip never shows `0` for a failed feed. The third stat (`totalEventsCount` derived) has
the same exposure when the events feed fails.

### F2 (Low) Loader test can time out on a cold run (observed once)
`app/routes/organiser.loader.test.ts:44`. The first case dynamically imports the route
module inside the test body; when run in the same vitest invocation as the matrix test the
first case hit the 5000 ms default ("all feeds ok" timed out, 1 failed / 35 passed). Run
alone it passed twice (5/5, about 1 s). The import cost lands on the first `it` and is
paid under the per-test timeout. Hoist the import to module level or give the file
`testTimeout: 15_000`. Not a correctness issue; a red-for-no-reason risk in `test:unit`.

### F3 (Low) Admin invite message: the one external caller now has an unread error state
`src/modules/admin-organisers/invitePersonApi.ts:112` (`fetchUpcoming`) wraps
`fetchOrganiserFutureOccEvents`. Callers `InvitePerson.tsx:83` and `InvitePersonWho.tsx:78`
use `retry: false` and read only `upcoming.data ?? []`. Before: a failed RPC gave `[]` and
the invite message silently omitted the dates. After: the query is in `error` and the
message silently omits the dates. Outcome unchanged, so no regression and the four admin
test files (which mock `fetchUpcoming`) still pass by construction. But the component now
holds an error nobody renders. Optional follow-up: show a one-line "Upcoming dates did not
load" next to the message box so the admin knows the message is thinner than usual.

### F4 (Info) "browser no-store" wording is inaccurate; the edge claim is proven
`app/routes/organiser.tsx:145`. `cacheHeaders()` with no tag emits
`Cache-Control: public, max-age=0, must-revalidate`, not `no-store`. Browsers may keep a
copy but must revalidate; functionally the same for this page. Comment nit only.

Proof of the edge claim (judge item 2), run through the real `loader` then the route's
`headers()` with a fake `supabase.rpc`:

| case | final response headers |
|---|---|
| all feeds ok | `Cache-Control: public, max-age=0, must-revalidate`; `Vercel-CDN-Cache-Control: public, s-maxage=0, must-revalidate`; `Vercel-Cache-Tag: organiser-<id>,organisers` |
| past feed failed | `Cache-Control: public, max-age=0, must-revalidate` only |

A failed feed therefore carries no cache tag and no CDN directive, so Vercel's edge has
nothing to store it under and `max-age=0` forbids it anyway. The all-ok page keeps its tag.
Note the all-ok page already has `edgeTtlBoundSeconds: 0` (s-maxage=0), so today neither
branch is edge-stored; the `feedFailed` branch is the guard for the day that TTL is raised,
which the loader comment already says.

### F5 (Info) SSR hydration concern checked and refuted
The loader's QueryClient holds the failed query in `error` state, but `app/root.tsx:194`
builds a fresh `createQueryClient()` for the server render and hydrates only
`dehydratedState`. `dehydrate()` keeps `status === "success"` only
(`@tanstack/query-core` `defaultShouldDehydrateQuery`; no override in `createQueryClient`).
So the server HTML shows the loading state for the failed feed, the client fetches it, and
there is no error-line-vs-loading hydration mismatch.
