## Verdict: BLOCK

One real defect (F1) reds a CI job on the PR head and would red any Node importer of a first-load
library; one merge conflict (F2) means the next push gets no `pull_request` checks at all until the
branch is rebased. Both are small to fix. F3/F4 are deep links that lose their id and should go in
the same round. Everything else is nits. With the flag OFF the behaviour is byte-identical to main
(every flag-off mutant I tried was caught). The bundle is byte-identical per route.

## Findings

### F1 (BLOCK) `src/lib/accountRouting.ts:38` -- `import.meta.env.X` crashes outside Vite; phone-qa job is red
The round-2 "zero first-load bytes" fix reads `import.meta.env.VITE_ENABLE_ORGANISER_P3` at module load
with no guard. Outside Vite (`import.meta.env` undefined) that is a TypeError at import. Playwright loads
spec files in plain Node: `tests/e2e-phone/organiser-refusal-copy.phone.spec.ts:3` imports
`src/modules/organiser/shared/selfServeErrors.ts`, whose line 12 imports `@/lib/accountRouting`.
- Reproduced (worktree of the branch, same node_modules):
  `npx playwright test --config playwright.phone.config.ts --list`
  branch: `TypeError: Cannot read properties of undefined (reading 'VITE_ENABLE_ORGANISER_P3') at src/lib/accountRouting.ts:38` then `Total: 0 tests in 0 files`;
  main: `Total: 534 tests in 21 files`.
- CI on the PR head confirms it: job `phone-qa` (run 41237611762, job 124644583121) failed with the same
  stack. The PR body lists phone-qa under "not runnable here"; it is runnable (`--list` alone shows it).
- Failing scenario: every phone-qa run on this branch is red, so no 390x844 / 360x640 phone spec runs.
  Any future spec, script or SSR path that imports accountRouting (a first-load lib that most account
  code reaches) fails at import the same way. main's accountRouting has no `import.meta.env` read.
- Fix that keeps the zero-byte property, both already in the repo: `src/lib/goingCheckin.ts:24-33` wraps
  the read in try/catch (default off), and `vite.config.ts:24-28` `define`s the keys so the build still
  replaces each access with a string literal (no env object inlined). Define
  `import.meta.env.VITE_ENABLE_ORGANISER_P3` and `_SELF_SERVE` there, read them inside try/catch,
  default to ORGANISER_HOME_PATH, re-run `npm run build && npm run check:bundle-budget` (the pin test
  in p3Landing.matrix already checks equality with `flags`), and run the phone config `--list` as the proof.
  Note vitest: `vi.stubEnv` still works with `define`d keys only if vitest.config does not define them;
  the pin test already runs under vitest, so check it stays green.

### F3 (medium) `src/lib/organiserAreaHome.ts:59` -- an R1 draft step loses its draft
`r1ToP3Path('/account/o/new/s1/venue')` -> `/account/p3/create` (any `new/*` -> create). P3's own rule for
the same URLs is the opposite: `src/modules/organiser/p3/shell/P3Routes.tsx:55-64` (`NEW_STEPS`
`'new/:seriesId/*'` -> `P3_PATHS.event(seriesId)`, comment "review r1 F6 ... so none falls to Home").
- Failing scenario: an organiser is mid-draft in R1 (series created at the name step, now on venue/date/
  time/cover) when the flag flips, or opens an R1 draft-step link from history. They land on an empty
  Create; the draft they already named is orphaned unless they find it in Events.
- The matrix row `['/account/o/new/s1/venue', '/account/p3/create']` (p3Landing.matrix.test.ts) pins the
  wrong target. Map `new/<seriesId>/*` (b not `what`/`name`) to `${P3}/events/${seg(b)}` and flip the row.

### F4 (low-medium) `src/lib/organiserAreaHome.ts:67` -- R1 go-live loses its series
`/account/o/go-live?series=s2&o=org1` -> `/account/p3/start?series=s2&o=org1`. P3's OnboardingFlow reads
only `o` (`src/modules/organiser/p3/onboarding/OnboardingFlow.tsx:106`); `series` is ignored, so the person
lands in page onboarding, not that event's go-live. R1 go-live URLs with `?series=` are real returnTo
values (`flows/doneState.returnToSeriesId` names them; P3NewFlow.exits.test row "R1 go live"). Map
`go-live` with a `series` query to `${P3}/events/<series>` (and drop `series` from the query); keep
`/start` only without one. The matrix row `['/account/o/go-live?o=a', ...]` does not cover `series`.

### F5 (low, copy, flag ON only) `src/lib/accountRouting.ts:380` + `:285-289` -- switcher path says "Continue"
`profileSides` builds the unfinished-dancer-with-organiser-intent side as `appWelcomeHref(f.newOrganiserTo ?? home)`.
`useProfileSides` (the ProfileSwitcher and SwitcherGate) supplies `organiserHomeTo` but no `newOrganiserTo`,
so with P3 live the onward returnTo is `/account/p3`. `onboardingEndLabel` names only ORGANISER_HOME_PATH
("Next: set up your organiser page") and P3_START_PATH ("Next: find or create your page"); `/account/p3`
falls to "Continue". On main (P3 on) the same person saw a named next step. Either pass the P3 start as
`newOrganiserTo` from useProfileSides or let `onboardingEndLabel` treat the P3 home like P3 start. Add the
switcher shape to newOrganiserLanding.test (it only tests the sign-in path with `newOrganiserTo` set).

### Nits
- N1 `OrganiserRoutes.tsx:100-107` `stickyLegacy` writes sessionStorage during render, and does so even
  when only `organiserP3` is on (self-serve off), where the redirect never fires. Harmless; an effect or
  a `p3AreaLive` guard would be cleaner.
- N2 "per tab" legacy only holds inside R1's own links: every door (dancer home, Options, Your areas,
  sign-in landing, the claim card, the Done screen) goes straight to P3 even in a legacy tab. That matches
  the handover text ("so R1's own links keep it") but the P3 You link copy "Use the old organiser area"
  reads as if the area stays chosen. Worth one sentence in the handover or the link's copy.
- N3 Storage blocked (private mode on some browsers, or site data blocked): `stickyLegacy` returns false,
  so only the exact URL with `?legacy=1` renders R1; the first R1 in-area link redirects to P3, with no
  message. Acceptable for a 7-day window; say so in the handover.
- N4 `r1ToP3Path` sends `/account/o/more` and `/account/o/more/help` to P3 Home although P3 has the same
  screens at `you/account` and `you/help` (`P3Routes.tsx:106-107`). Nothing lost, one extra tap.
- N5 `DancerHome.tsx:25` imports `ORGANISER_AREA_HOME_PATH as ORGANISER_HOME_PATH` from the same module as
  the line above it, so the file keeps a name that now means something else. Rename at the use sites.

   `AREA_HREF.organiser`, the DancerHome links, the Done screen's no-id branch (`organiserAreaHome(flags)` ->
   `/account/o`, label "Open your organiser home"), PublicClaimCard (`?o=` only while live), and
   `r1AreaRedirect` returning null before touching storage. Mutation table (worktree, the PR's six test
   files + accountRouting.test, baseline 364 green):

   |---|---|
   | ORGANISER_AREA_HOME_PATH always `/account/p3` | 8 tests red (env pin x6, Options/areas off, claim off) |
   | PublicClaimCard always appends `?o=` | PublicClaimCard.test "email matches, mailbox proven" (href `/account/o`) |

2. Flag ON matrix: every person shape x entry in the brief is a row in p3Landing.matrix,
   p3LandingWelcome.table, newOrganiserLanding, loginDeadEnds or p3Redirect.mount, and I re-ran them

   stays R1; the wizard's `goHome` (`ProfileWizard.tsx:119`) goes to R1 Home -> P3 Home, one hop, no cycle.
   R1 `*` -> R1 Home -> P3 Home; P3 `*` -> P3 Home. `/account?o=x` -> `/account/o?o=x` -> `/account/p3?o=x`.
   Old `/account/new|series/:id|team/:org` -> R1 -> P3 (2 hops, tested). Signed-out: the redirect is above

   R1's AuthGuard with `?legacy=1` in returnTo, so the choice survives too. Deep links that lose their id:
   F3 (draft steps) and F4 (go-live series). Query/hash: kept everywhere else, `legacy` dropped (tested).
