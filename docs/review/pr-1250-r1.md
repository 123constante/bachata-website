## Findings, ranked

### F1 (medium, data-source fact wrong; fix prose + add one test row): `ticket_type_upsert_v1` gates the update branch too

Live body (pg_proc, read 2026-11-01 in this review), after the `SELECT * INTO v_type ... FOR UPDATE` in the
update path:

```
PERFORM public._require_onboarding_complete_v1(ARRAY[v_type.organiser_id]);  -- onboarding S8 gate
```

So the function gates BOTH branches (create: `ARRAY[v_org]`; update: `ARRAY[v_type.organiser_id]`), and
`ticket_type_set_status_v1` gates only `p_status = 'on_sale'` (that half of the claim is right). The PR says
"create branch only" in four places:

- PR body, "Data source" and the F-11 bullet.
- `docs/handover/p3-wt-gate.md` line 12 ("gate line in the create branch (`IF v_id IS NULL`)").
- `scripts/onboarding-write-doors.json` `_doc` ("ticket_type_upsert_v1 gates its create branch").
- `src/modules/organiser/p3/tickets/__tests__/gate.matrix.test.tsx:9-11` (file comment) and the describe at
  `:121` ("Edit an existing ticket (upsert update branch: not gated)"), whose single test title promises
  "changed: saves, never opens the gate" but its body only proves "untouched sends nothing" (there is no
  changed-edit row at all).

Failing scenario (flag ON, the page unfinished, 1 page on prod has 2 paused ticket types): open Tickets, Edit
an existing ticket, change the capacity, Save. The server raises `onboarding_incomplete`; `ticketsApi` throws;
`TypeSheet.tsx:134-138` routes it through `gated(...)`, so the shared sheet opens and no "Try again" shows,
which is the right behaviour. But no test pins it, and a reader of the config `_doc` or the test would believe an
edit cannot be refused. Fix: correct the four spots, add the "edit, gate on, refused" row to the matrix (and
the "changed: saves" row the title already promises). Owner Approve at head: YES, the move to `gated` is correct
and the live guard already counts both doors (Part B `gated=10`, healthy, flag OFF).

### F2 (low, logic): a held dry-run refusal in Repeat never clears, even after the status re-read says pass

`RepeatSheet.tsx:155-156` keeps `refusal` in state once a dry run was refused (the status-unknown path), and
`:192` makes `gateHeld = refusal ?? ...`. Save calls `gate.recheck()` (`:208`), but a refetch that now answers
`pass` (details finished on another device, or the flag flipped off) changes nothing: `refusal` is never reset,
so Save keeps opening the sheet and never sends until the Repeat sheet is closed and reopened.

Failing scenario: status read fails once (offline blip), the dry run is refused and held, the person taps "Not
now", finishes their details in another tab, returns to the still-open Repeat sheet, taps Save: the gate sheet
opens again with nothing left in it. Fix: clear `refusal` when `gate.answer.s === 'pass'` after a recheck (one
line in an effect), and add that row to `gate.fixround` 5.

### F3 (low, mirror fidelity): the predicted refusal names the wrong page on a multi-page series

`gateRule.ts:36` returns `mine[0]` in the STATUS order (`organiser_onboarding_status_v1` sorts
`organisers` by name, then id), while `_require_onboarding_complete_v1` names the first unfinished member page
in TARGET order (`ORDER BY min(t.n)` over `p_organiser_ids`, i.e. `event_series_p5.organiser_ids` order). For
the 6 series run by 2+ pages, when every page the person is on is unfinished, the gate sheet's Continue can point
at a different page than the server's refusal would. The test "a refusal names the first of the event's pages the
person is on" (`gateRule.matrix.test.ts:34`) enshrines the client order: it expects `x` for organisers `[x, a]`
and targets `['a', 'x']`, where the server would say `a`. Fix: iterate `targets` and pick the first that is in
`mine`; flip the expectation to `a`.

A second, theoretical asymmetry for the record: with empty `organiser_ids` (571 of 758 series) the server
targets `get_current_user_organiser_ids()` (entity_members with role owner/manager/contributor, plus legacy
claimed entities), while the client uses every page in the status read (every entity_members role). A page held
under any other role would count for the client only. No such role is in play on the paths reviewed; noted, not
scored.
