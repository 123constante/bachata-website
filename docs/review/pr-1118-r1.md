Reviewer: Fable (independent; nothing under `src/` touched). Brief: `docs/briefs/review-1118-r1.md`
(branch `brief/review-1118-r1`). Target: `claude/p3-w4b-onboarding` at `32b6a78` (PR head at review

## Verdict: PASS with should-fix

The build does what the owner picked (new account = A, unfinished profile = B at the tap, return copy
as drawn, no returnTo carry, no-row frame keeps Message us, flag off, R1 unchanged), the tap gate reads
the same fact the server checks, the gate matrix goes red under every mutant tried, and nothing sends
a claim, ask or create while the profile is unfinished. But the PR is **red on real CI at its head**
(S1: a test mock this PR did not update), the PR body's CI claim does not match what CI shows (S1),
the walk the "Phone QA" section leans on is protected nowhere in CI (S3), and the client gate blocks
an admin the server would let through (S2). S1 must land before merge; S2 and S3 are the builder's
call to fix in the one fix round or to record as accepted.

## Should-fix

### S1. Real CI is red: `unit (Europe/London, full)` fails on the PR head; the PR body says otherwise

- `src/modules/organiser/__tests__/draftOrganiser.matrix.test.tsx` (its `vi.mock('@/hooks/useAuth')`)
  with `src/modules/organiser/home/onboarding/OnboardingView.tsx:49`
  (`useContext(ProfileGateContext)`).
- What happens: the test mocks `@/hooks/useAuth` and returns no `ProfileGateContext`; the PR makes
  `OnboardingView` read that export on every render, so the "stranger: no organiser, so onboarding"
  case throws `No "ProfileGateContext" export is defined on the "@/hooks/useAuth" mock`. Vitest
  reports it as an unhandled error and the job exits 1. Real CI at `32b6a78`: 659 files, 18402
  tests passed, **1 error, job failure** (run 40714468151). `main` at `48087d5` is green on the same
  workflow (run 40697338532). The two tz-sensitive unit jobs are green because they run a subset.
  Reproduced locally on the branch: `npx vitest run src/modules/organiser/__tests__/draftOrganiser.matrix.test.tsx`
  prints the same error.
- The PR body's per-job table says the unit job is green but for "17 failed in 5 files" that
  "fail identically on main". Real CI shows 0 failed tests and 1 unhandled error that main does not
  have. The 17 are a sandbox artefact; the 1 is this PR's.
- Fix: give that mock a `ProfileGateContext: createContext(null)` the way the PR already did for
  `OnboardingSignOut.test.tsx` and `addPage.matrix.test.tsx`. Three more files mock `@/hooks/useAuth`
  without it and import the organiser home or switch tree (`switch/__tests__/Switch.test.tsx`,
  `__tests__/consistency.render.matrix.test.tsx`, `src/pages/__tests__/AccountOrganiserAction.test.tsx`);
  CI shows only one error, so they do not reach `OnboardingView` today, but check them while there.
  Alternatively make the read tolerant of a missing export, but the mock fix is smaller.
- Check that would have caught it: running the full `npm run test:unit` and reading the Errors
  line, not only the failed-tests count. Vitest's "Unhandled Errors" block exits 1 even when every
  test passes.

### S2. The client gate blocks an admin the server exempts

- `src/modules/organiser/home/onboarding/profileGate.ts:19-24` and
  `src/hooks/useProfileCompletion.ts:28-50` (no admin notion) against
  `_require_complete_dancer_profile_v1` on prod (`IF public.is_admin() THEN RETURN;` before any
  profile read).
- Failure scenario: an admin account with no dancer row (prod today: 4 admins, **2 with no dancer
  row**, 0 incomplete; read-only count) opens P3 Welcome and taps Create or Claim. The client fact is
  `no_profile`, so the tap shows the no-row frame ("Your account does not have a dancer profile yet...
  Message us on WhatsApp") and never opens the sheet. The server would have accepted the claim or
  create. R1 at `/account/o` lets the same admin through today (no tap gate), so P3 is a regression
  for those two accounts. Brief must-check 3 names "blocks ... an admin" explicitly.
- Fix options: (a) carry an `isAdmin` on `ProfileGateValue` (the app already knows admin status
  where it routes admins) and let `tapGate` return `open` for it; or (b) record it as accepted (admins
  use R1 or the admin area) in the design record's shape table, with the count. Either way the gate
  test gets a row "admin, no row / incomplete -> opens today's sheet".
- Check that would have caught it: the gate matrix has 7 completeness shapes but no admin row,
  while the server body it mirrors has an admin branch. A matrix row per server branch.

### S3. The walk is protected nowhere in CI, and the e2e gate entry is a permanent skip

- `package.json` `test:e2e` (adds `tests/e2e/walk-p3-w4b-onboarding.spec.ts`),
  `.github/workflows/e2e-smoke.yml:76-85` (env has `VITE_ENABLE_ORGANISER_SELF_SERVE` only, no
  `VITE_ENABLE_ORGANISER_P3`), `playwright.phone.config.ts:32` (`testDir: './tests/e2e-phone'`).
- What happens: the spec skips itself when `/account/p3` is not mounted
  (`walk-p3-w4b-onboarding.spec.ts:33`), and the e2e gate's dev server never mounts it; `phone-qa`
  runs a different directory. So every number in the PR body's "Phone QA" section (contrast, 44px,
  width, sheet geometry, no page scroll) comes from the builder's sandbox only and will not go red in
  CI when a later PR breaks it. The PR body says this honestly for the e2e gate; it does not say it
  for `phone-qa`, and "in the `test:e2e` list by name" reads as protection it is not.
- Fix: the smallest is `VITE_ENABLE_ORGANISER_P3: 'true'` in e2e-smoke's env (the other P3 specs
  already in the list would then run against a mounted P3 too; not verified here how they get P3
  today). If that is the owner's separate call, as the handover says, then the PR body should state
  "not protected in any CI job" rather than list the spec as if it were, and the design record's
  "Self-check numbers" should say "sandbox only".
- Check that would have caught it: `grep -c skipped` on the e2e-smoke job log for this spec, or a
  guard that fails when a spec in the `test:e2e` list reports every test skipped.

## Notes

### N1. `/app/*` first load is 373.7 KB on the branch, 373.6 KB on main (budget 374 KB)

`npm run build` + `npm run check:bundle-budget` on both, same env as `perf-budget.yml`. The PR body
says "identical"; the budget output says +0.1 KB (`root` and `AnimatedRoutes` hashes change, each
under the 0.05 KB rounding; the `/event` and `/classes` routes move by 0.1 KB too). Still `[ok]`, but
headroom is now 0.3 KB; the next first-load byte on this route is a budget failure. Nothing to do
here beyond correcting the body.

### N2. The confirmation line comes back on a refresh of P3 Home

`src/modules/organiser/p3/screens/HomeScreen.tsx:21-31`. The line rides `location.state`, which the
browser keeps across a reload of the same history entry, so "X is yours. You can now manage it."
shows again after every refresh of that entry, and the "Loading your events..." guard engages again
while the home read is in flight. Harmless, but the line says something just happened when it did
not. Optional: `navigate(pathname, { replace: true, state: null })` after first render, or key the
line to a one-shot in sessionStorage the way `ClaimNotice` does.

### N3. The race guard has one hole: a refetch that still says "no page"

`HomeScreen.tsx:49-56`. After a claim or create the Home waits only while `home.isFetching`. If that
refetch finishes with `organisers` still empty, or errors (the query keeps the stale empty answer and
`isFetching` goes false), Home replaces to Welcome and the confirmation is dropped with no line. The
walk's fake answers at once, so it never meets this. Rare on prod; worth a line in the design record
rather than code.

### N4. "come back to Welcome" on the Add a page variant

`profileGate.ts:28` (`GATE_RETURN_TEXT`). A person who already holds a page (admin-made pages have
members whose dancer profile may be unfinished) opens **Add a page** from You, taps Create, and the
gate sheet promises "you come back to Welcome". `returnTo` brings them back to this same screen,
titled "Add a page" with a back to You. Same screen, wrong name. Owner said the copy ships as drawn,
so this is a note: a second string for the `firstRun === false` case would fix it in one line.

### N5. Walk and matrix cover the gate on P3 only; R1 proof is the one row set

The R1 rows in `p3Onboarding.gate.test.tsx` (3 taps, unfinished shape, `look="r1"`) plus the
default-context reads (`useOrgSurface` falls back to `R1_SURFACE`, `useSheetLook` to `'r1'`) are what
prove R1 unchanged. Read through: the R1 branch of every new conditional is the old code path
(`SheetView` keeps `bg-black/60` and `focus()` with no options; `OnboardingView` keeps `ORG_PATHS.home`
through `surface.paths.home`; `goDone` keeps its two-argument form). Fine; noting where the proof
lives.
