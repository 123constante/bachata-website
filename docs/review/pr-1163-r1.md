# Review r1: PR 1163 (bare /auth opens sign-in), head a554843

Independent, read-only review against `origin/main` (a1d0fa6). The reviewer did not build this PR.
Diff: `src/pages/Auth.tsx`, `src/lib/focusMode.ts`, `src/lib/__tests__/focusMode.test.ts`,
`src/pages/__tests__/AuthDefaultSignin.test.tsx` (new), `tests/client/signupFocusChrome.test.tsx`.

**Verdict:** the logic change is correct and well pinned. One caller still depends on the old
"bare /auth means sign-up" rule (finding 1): fix it before merge. Everything else is a nit.

## Findings (most severe first)

### 1. The team invite link still points at bare /auth, so an invitee now lands on "Welcome back"
- **Where:** `src/modules/organiser/edit-in-place/teamPickerModel.ts:218` (`inviteShare`). Used by
  `src/modules/organiser/edit-in-place/TeamSheet.tsx:155` and `src/modules/organiser/team/AddSomeone.tsx:84`.
  Pinned by `src/modules/organiser/edit-in-place/__tests__/teamPicker.matrix.test.ts:230`, which still
  expects `.../auth` while its own title says "is a sign-up link".
- **What is wrong:** an organiser shares an invite that says "Join Bachata Calendar and make your
  dancer profile, so I can add you to the X team" and links to `https://www.bachatacalendar.com/auth`.
  The function's own doc comment calls it "a link to sign up". It relied on the old default. After
  this PR the person who taps it, who has no account yet, sees **"Welcome back"** with the sign-in
  form and the normal site chrome, not "Join the community".
- **Failing input:** tap the shared invite URL `<origin>/auth` while signed out. On main it showed
  the sign-up steps; on a554843 it shows sign-in. They can still get through: typing a new email on
  sign-in calls `switchToSignup` (Auth.tsx:283-295 / 349-352) and moves them to sign-up with a notice.
  That is one wasted step plus a screen that doesn't match the message they just read.
- **Fix:** `${origin}/auth?mode=signup` (or `buildSignInHref(null, 'signup')`) and update the matrix
  test's expected URL. This is a one-line change that belongs in this PR.
- **Severity:** fix before merge. **CONFIRMED** (by reading the code; no browser walk was done).

### 2. The "which mode" rule is written twice: Auth.tsx and focusMode.ts each have their own copy
- **Where:** `src/pages/Auth.tsx:122` and `src/lib/focusMode.ts:31-33`.
- **What is wrong:** the page decides what to draw (`get("mode") === "signup"`), and the chrome
  decides whether to use focus mode (`params.get('mode') === 'signup'`). Today the two agree on
  every shape tested below, so there is no bug yet. CLAUDE.md's definition of done asks for "one
  shared mapping for any fact shown on more than one screen". The PR does make the two copies
  identical, where on main they differed (`mode || "signup"` vs `mode !== 'signin'`).
- **Failing input (mutation M3, survives):** make Auth.tsx case-insensitive
  (`get("mode")?.toLowerCase() === "signup"`). All 56 tests in the three suites stay green, yet
  `/auth?mode=SIGNUP` would then draw sign-up inside the normal site chrome with no focus bar.
  Nothing pins the two copies to each other, and no test covers the `mode=SIGNUP` shape.
- **Fix (optional):** export one `authModeFromSearch(search)` from `focusMode.ts`, use it in
  Auth.tsx, and add `mode=SIGNUP` and a repeated mode to the AuthDefaultSignin table.
- **Severity:** nit (the duplication predates this PR). **CONFIRMED** (mutation run locally).

### 3. A sign-up started at bare /auth before the deploy reopens as sign-in after it
- **Where:** `src/pages/Auth.tsx:122` together with `readCodeStep(mode)` at :127.
- **What is wrong:** on main, someone on bare `/auth` walked the sign-up steps without
  `mode=signup` ever being added to the URL (`handleRoleContinue` only sets `userType`), and D7
  stored the code step under `signup`. If they reload that tab after this deploys, the page reads
  `signin`, so the stored step doesn't match: the code box is not restored and the sign-in form
  shows instead. The 10-minute window limits this to people mid-sign-up at deploy time.
- **Severity:** nit, lasts minutes and fixes itself. **PLAUSIBLE** (follows from the code; not run).

### 4. Analytics: `auth_viewed` for bare /auth now reports `signin`
- **Where:** `src/pages/Auth.tsx:170`.
- The value is correct: it follows the screen that is drawn (sign-in for bare /auth, empty, junk
  or uppercase mode; sign-up only for `mode=signup`), and `magic_link_sent` at :336 follows
  `isCreateAccount`. The side effect is that any dashboard comparing signup vs signin
  `auth_viewed` will show a step change on the deploy date: bare-/auth views move from `signup`
  to `signin`. Worth one line in the PR body.
- **Severity:** nit (annotate only). **CONFIRMED**.

### 3. Auth.tsx mode parsing
`get("mode") === "signup" ? "signup" : "signin"`: unknown, empty, uppercase and absent all give
sign-in; repeated values use the first. The fallbacks no longer depend on `userType`. `returnTo`
is read separately (`sanitizeReturnTo`, :112) and is kept in the tab links (:205-206), in
`switchToSignup` (:240-243) and in the callback URL (:308-311). The AuthDefaultSignin table runs
every mode with and without a returnTo. `AuthCallback.tsx:115,222` is untouched; the callback URL
always carries an explicit mode (:308).
