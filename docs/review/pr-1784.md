## Verdict: BLOCK

One must-fix bug (B1 below). It does **not** risk a wrong charge, but a buyer with an applied code can get stuck on "Checking…" with Continue disabled and no request in flight. It is a small fix. Everything else passes, and the nits are optional.

## Hard-tier: PASS

No path charges the wrong amount. `ticket_checkout_reserve_v5` checkpoint (b) requires `p_expected_total_pence = v_sub - v_disc_sum + v_fee` **exactly**, or it returns `price_changed` with no order. Any client total that is too low or too high is refused, never accepted. The client maths also matches the server for every basket the preview accepts (item 1).

## Must fix

### B1. "+ then −" inside the 400 ms debounce leaves the code stuck on Checking
`TicketPickerB1.tsx` `step()` sets `promo = {status:'checking'}` on every tap while a code is applied. The re-price effect only fires when `pricedKey.current !== key`. Here is the sequence:
1. The code is applied for basket K1, so `pricedKey = K1`.
2. Tap +. The key becomes K2 and a timer is scheduled.
3. Tap − before 400 ms. The key is back to K1. The cleanup clears the timer, and the new effect run sees `pricedKey === K1` and returns.
4. `promo` stays `checking` for good. No preview runs, the stub shows "Checking…", Continue stays blocked ("Wait while the promo code is checked."), and the only way out is Remove.

**Reproduced** with a probe test on the PR head. It ran in a scratch worktree and was not committed. Steps: add Full Experience, apply SAVE10, then `add` and `Remove one` back to back, then wait 1.2 s. Result: stub text `SAVE10Checking…Remove`, `previewPromo` calls = 0.

Suggested fix, either one:
- in the effect, when `pricedKey.current === key` and `promo.status === 'checking'`, restore the last applied result; or
- keep the last applied state in a ref, and do not set `checking` in `step()`. Let the effect set it when the timer fires, since `promoView` already blocks Continue with "Tap Apply to update…" while the key mismatches.

Add the probe as a regression test (it fails on the current code).

## Nits (optional)

- **N1. A held price_changed survives Apply and Remove.** `applyPromo`/`removePromo` do not call `setHeld(null)`. Remove after a promo-priced `price_changed` leaves the bar showing the held (discounted) total with no code. Continue then sends that total without `promo_code`, the server answers `price_changed` again, and the buyer goes through one extra round. The reverse (Apply over a held no-code total) behaves the same way. This fails safe because of checkpoint (b), but the bar can show the wrong amount until then. Fix: `setHeld(null)` in both.
- **N2. Per-line `below_minimum` / `no_discount` give false refusals.** The handover already notes this. The preview refuses a line whose net is 1–29p, or whose discount is 0, even when the basket as a whole would pass reserve v5. This fails closed (buyer refused, never undercharged). Line nets that are each 0 or ≥ the minimum always sum to 0 or ≥ the minimum, so the client never accepts what the server refuses.
- **N3. List price vs effective price.** `discountedTotal` uses `t.pricePence` (the list price). The server uses `_ticket_effective_unit_price_v1(type, night)`. When they differ, checkpoint (a) returns `price_changed` and the held total wins. That is fail-safe and the same as the no-code path.

## Checklist (brief items)

1. **Discount maths: PASS.** The preview's per-line discount is `_ticket_promo_unit_discount_v1(kind, value, v_unit) * qty`, the same expression reserve v5 uses per line, and `previewBasketPromo` sums them. Fee: reserve charges `fee_per_ticket * v_total_q` (all tickets, free ones included) only when `v_net <> 0`. `discountedTotal` uses `feePerTicket * sum.count` (all tickets) only when `net > 0`, so they match. `promoLines` sends only lines with `pricePence > 0`, so free lines are never previewed.
2. **expected_total_pence: PASS.** `buildPickerBody` precedence is held, then promo, then list. `payPence` (`heldNow ?? promoTotal ?? sum`) is passed as `promo.totalPence`, so a held `new_total_pence` (which reserve computes *with* the code's discount) wins. Checkpoint (b) is an exact-equality guard, so a lower client total is never accepted.
3. **Stale code: PASS, apart from B1.** `pickerPromoKey` covers the basket, the night and the paid-line list prices. `promoView` gives `sendCode`/`appliedDiscountPence` only when `state.key === key`, so a stale price is never shown or sent and Continue is blocked. Remove sets the state to idle and clears the input, so `sendCode` is null and there is no `promo_code` in the body. A refused or invalid code leaves `appliedDiscountPence` null, so the bar shows the list total and nothing is sent.
4. **Free after discount: PASS.** With net 0, `discountedTotal` = 0 (no fee) and the body carries `promo_code` plus `expected_total_pence: 0`. Reserve v5 makes a 0-total order with fee 0, and `r.kind === 'free'` takes the existing `/tickets/thanks?o=…&free=1` path. This is covered by a test in the PR.
5. **Out-of-order replies: PASS.** `promoSeq` is bumped by every `pricePromo`, every scheduled re-price and Remove, and a reply whose `seq` is not current is dropped. The stuck state in B1 is a separate debounce problem, not a race.
6. **Tests/tsc: PASS.** On the PR head, `npx vitest run src/modules/tickets`: 28 files, 917 passed. `npx tsc --noEmit -p .`: exit 0. `tsc -p tsconfig.app.json`: 0 errors in the touched files. The 157 pre-existing errors are the same count as on `main`.
