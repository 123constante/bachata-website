## F-27 DATES-100

**Prod source of truth (read-only, prod `stsdtacfauprzrdebmzg`, 2026-10-31).**
`admin_event_workspace_p5(p_series_id uuid, p_before date DEFAULT NULL, p_limit integer DEFAULT NULL)`:
- page: `o.occurrence_date < p_before` (strict), `ORDER BY o.occurrence_date DESC`, `LIMIT COALESCE(p_limit, 100)`; `p_limit` outside 1..200 raises `invalid_input` (P0001) (body lines 41-44, 93-95).
- `meta.has_more` = exists a date older than the page (lines 99-103); `meta.next_before` = `min(occurrence_date)` of the page, only when `has_more` (lines 50, 152).
- `meta.total` = `count(*)` of the series' occurrence rows, cancelled included (line 111).
- `meta.counts` = `upcoming` / `past` (both `lifecycle_status IS DISTINCT FROM 'cancelled'`, split on the series' local today), `cancelled`, `changed`, `breaks` (count of `removed_dates`) (lines 112-121).
So the builder's reading in the handover is accurate, and every field the client parses exists.

**Prod shapes (counts only).** Series over 100 dates: 1 (132, the max). Max future dates in one series: 57. Series with two rows on the same date: 0. Series whose `removed_dates` overlap a stored date: 0. Series with breaks: 16.

**Anchor and paging.** `useOlderDates` (olderDates.ts:56-64) anchors on the FIRST read's `meta.next_before` (`ws0.nextBefore`, AllDatesScreen.tsx:38-41), and `fetchOlderDates` (olderDates.ts:38-47) walks `p_before = page.next_before` at `p_limit` 200 until `has_more` is false. Strict `<` on the server plus `next_before = min(date)` of the page means no date is read twice and none is skipped, as long as no two rows share a date (prod: 0 series; a latent skip only if that ever changes, since the anchor is a date, not an id). `withOlder` (olderDates.ts:49-55) dedups by id, so an anchor that moves newer after a mutation (the newest page shifts) cannot double a date. The 657-date test (`allDates100.matrix.test.tsx:84-97`) proves three pages of 200 with the right anchor.

**Counts before equal counts after.** `countsOf` (dates.ts:93-109) on a partial read: Coming and Breaks come from the slice, which is whole for them (every future date is in the newest page unless `readIsFull`; breaks are the series row's); Past = `meta.total` minus the loaded future rows plus past breaks (every stored row not coming up is past, cancelled or not, which matches the `past` filter at dates.ts:72); Cancelled = `meta.counts.cancelled`, which matches `facts.state === 'cancelled'` (dateFacts.ts:52, one-to-one with `lifecycle_status`). Own changes is an honest floor ("N+"), since the server's `changed` does not count a date's own time. The partial Past count is derived from `total`, not from the server's `past`, so the client's London today and the server's series-local today cannot disagree. Verified by the matrix at `allDates100.matrix.test.tsx:65-82` on 0, 1, 57 future, exactly 100, 101, 132, and by the render test at 120-135 (Past 75 and Cancelled 7 before and after the tap).

**Button, note, error, sheets.** "Load older dates" renders only when `ws.hasMore && ws0.nextBefore` (AllDatesScreen.tsx:40, 75); on an older read of the RPC that sends no `next_before` the screen falls back to `partialOf`. The note names the button that is on screen (dates.ts:118-126) except in the error state (F1). The error state says what to do and has Try again (AllDatesScreen.tsx:70-74, test 137-147). `DateSheets` receives the merged `ws` (line 83) and DateSheet finds its date in `ws.dates` (DateSheet.tsx:389), so cancel, uncancel and edit see loaded older dates.

**`keepPreviousData` and a filter change.** A filter change is local state and does not touch the query key, and the counts are computed from `ws`, so no stale count follows a filter change. The stale window is elsewhere (F7).
