## Findings

### F1 (fix before merge): "no page scroll on open" is vacuous, because the window never scrolls in P3
`tests/e2e/walk-p3-series-pictures.spec.ts:103` and `:109`/`:114` read and set `window.scrollX/scrollY`. In P3 the document is exactly one viewport tall (measured: `scrollHeight 844 = innerHeight 844`, body `overflow: hidden auto`). The page scrolls inside `.p3-main` (`p3.css:62`, `overflow-y: auto`). So:
- `window.scrollTo(0, scrollHeight)` on line 103 does nothing, and the "at page bottom" premise of the save-bar check never happens. Only `scrollIntoViewIfNeeded` moves `.p3-main`.
- `before` on line 109 is always `[0,0]`, and so is the value after opening the sheet.

**Failing scenario (mutation).** Add `useEffect(() => { document.querySelector('.p3-main')?.scrollTo(0, 0); }, [])` to `PicturesSheet`. Opening the sheet now jumps the page back to the top. **The spec stays green, 6/6 light.** With `.p3-main.scrollTop` added to the measurement, the same mutant goes **red on 4 of 4 shape tests**, and the unmutated code stays green 6/6. Measured `.p3-main.scrollTop` before opening was 786 for 1, 2 and 30 pictures, and 844 for 0, so the page really is scrolled before the sheet opens.
**Fix:** measure `[window.scrollY, document.querySelector('.p3-main')?.scrollTop ?? 0]`, as `walk-p3-w4b-onboarding.spec.ts:113` and `p3-gate-sheet.spec.ts:146` already do, and scroll `.p3-main` to its bottom (not `window`) on line 103.

### F2 (nit): the tap and contrast audit covers only the open dialog, so the page's Pictures row is never sized
`audit()` (`spec:58`) only walks `[role="dialog"]`. **Mutant:** the page row `p3-d-pictures-open` set to `minHeight: 30, height: 30` (DetailsScreen.tsx:140). **12/12 green.** **Fix:** assert `p3-d-pictures-open`'s box is at least 44 tall, or run the tap filter over `.p3-main` too.

### F3 (nit): the untouched-save test's click is conditional
`spec:157`: `if (await save.isEnabled()) await save.click();`. If the save is disabled, nothing is clicked, which happens to be the correct outcome. The mutant that matters (gallery `same: () => false` in `data/details.ts:81`) enables Save and **is caught** (light and dark red). Still, write down the expectation: `await expect(save).toBeDisabled()` (or the tray's "no changes" state) and then the envelope check. A build that sent a command on open/close without enabling Save is caught by line 148, which I checked with a separate mutant.

### F4 (nit, pre-existing, shared `Sheet`): Close scrolls out of view in a long sheet
At 30 pictures, after scrolling the sheet to its end, Close sits above the viewport (measured at 390x844 and 360x640, light and dark). The sheet head in `Sheet.tsx` is not sticky. Done is now pinned, so there is always a way out. This is not a regression from this PR. If it is wanted, it is a separate change to the shared `Sheet` and `.p3-sheet-head`.

### F5 (nit): the formats walked are recurring + festival only
Prod has `course` and `one_off` series with pictures (see the survey below). Their row runs the same non-festival branch (`DetailsScreen.tsx:75`, `festival = format === 'festival'`), so the risk is low. Adding one `one_off` shape would make that coverage explicit instead of assumed.

### F6 (nit): cold-server flake in the new spec
My first run on a cold dev server failed `0 pictures` and `1 pictures` (light), the first test in each worker. The next 3 full runs were green (12/12). I did not keep that error text. The likely cause is the 20 s `p3-details` mount wait (`spec:34`) during first compile. In CI this spec runs last in `test:e2e:p3`, so the server is warm, and CI was green. I recorded it rather than chase it.

## Q3: the product fix
Measured with a separate throwaway spec (not committed) at 390x844 and 360x640, light and dark, with 0, 2 and 30 pictures, keyboard-free:
- **Foot is inside the viewport**: 390x844 foot 775 to 844, Done 784 to 828. 360x640 foot 571 to 640, Done 580 to 624. `elementFromPoint` at Done's centre hits Done in every case.
- **No overlap at 30**: with the sheet scrolled to its end, the last picture row ends at 706 and the "limit reached" note at 763, both above the foot's top at 775 (390x844). At 360x640 they end at 501 and 559, above 571. In the middle of the scroll, rows go under the foot as expected for a sticky foot.
- **Readable**: the foot background is opaque `var(--sheet)`, the same as the sheet in both schemes (light rgb(255,255,255), dark rgb(42,45,50)). Contrast is at least 4.5 (the spec's audit, and the M6/M7 mutants show it bites).
- **z-index**: the foot has no z-index. It is the last positioned sibling, so it paints over the earlier `position: relative` `.p3-photo` and absolute `.p3-photo-x`. The hit test confirms Done is on top.
- **Safe area**: the foot's `bottom` and negative margin both use `-16px - env(safe-area-inset-bottom)`, which cancels the `.p3-sheet` padding exactly (`p3.css:178` vs `:280`). That is the same contract as the other users. Headless Chromium reports an inset of 0, so a real non-zero inset is **not verified**.
- **Right class**: yes. It is the same class used by `GateSheet.tsx:63`, `StackSheet.tsx:133` and `RepeatSheet.tsx:259`, with no new CSS. The others put a `.p3-sheet-body` (`flex: 1 0 auto`) above the foot. Here the siblings are direct flex children of `.p3-sheet` and do not shrink below their content (the measured no-overlap confirms that), so a body wrapper is not needed.
