# #1033 S4 front-door screens: phone walk, every screen x every shape

Branch `claude/s4-add-organiser-screens`, brief `briefs/s4-walk.md` (branch `brief/s4-walk`). Definition of done
step 4 (browser walk at 390x844 on prod-shaped data) for the three admin screens on `/admin/organisers/front-door`:
**Add**, **Organisers** and **Needs you**, plus the entry button on `/admin/organisers`.

## How it was walked

The admin screens sit behind an admin sign-in that a walker cannot get on a Vercel preview, so the REAL screens
were walked locally on the phone suite's fake Supabase (`playwright.phone.config.ts`; nothing leaves the machine).
`tests/e2e-phone/frontDoorFake.ts` adds an ADMIN session (`admin_is_admin` -> true) and scripted answers for the six
front-door RPCs (`admin_list_organisers_front_door_v1`, `admin_needs_you_v1`, `admin_add_organiser_v1`,
`admin_send_organiser_invite_v1`, `admin_set_run_by_us_v1`, `admin_resolve_claim_v1`) in the shapes
`frontDoorApi.ts` parses, and records every call. `tests/e2e-phone/front-door.phone.spec.ts` is the table-driven walk:
37 cases at 390x844, the prod shape of each of the three screens again at 360x640.

Every case asserts: no sideways scroll; every control >= 44 px tall in px (a 24 px switch counts its >= 44 px label
row); axe colour contrast >= 4.5; every disabled control has a visible reason via `aria-describedby`; copy that names
the Run by us switch matches that switch's state; copy that points at a control (Try again, the list, Add, Run by us,
the existing page) has that control on screen; no text wider than its own box. Plus per case: empty states offer an
action, the untouched Add submit sends nothing (0 RPC calls after Enter and a forced tap), the hint under Run by us
matches the switch both ways, Run by us sends no `contact_email`.

## Shapes

- **Organisers**: prod (owner's phone 2026-10-25: All 48 = Run by us 42, Invited 0, Joined 2, Live 4, with
  "a2b Dance Academy" live and "Agapi Musicality Dance Project" run by us); the Invited 0 group tapped; empty; one row;
  150 rows (over the 100-row API cap); very long, unbroken, null and blank names; every invite status (none, queued,
  sent, failed, skipped, plus queued+requested) on every chip; send and Run by us answers; loading, error, network
  failure.
- **Needs you**: prod (badge 23, one group "Quiet for 30 days (23)", Tropicana, Sparkle Up, Salsateca, Crouch End ...
  each with Open the page); every group the model has (`email_mismatch_claim`, `join_request`, `access_request`,
  `quiet_30_days`) with server detail, a long unbroken email and an item with no organiser; a refused Approve; empty;
  loading, error, network failure.
- **Add**: untouched; Run by us on/off; every outcome (invite queued, run by us, no email, already exists, person
  reused, `email_has_login` warning); every code in `ADD_ERROR_TEXT` (ORGANISER_NAME_REQUIRED, CONTACT_NAME_REQUIRED,
  EMAIL_INVALID, CITY_REQUIRED, PERMISSION_DENIED, INVALID_PAYLOAD), an unknown code, and a network failure.

The brief also lists "duplicates, invite requests, failed invites" as Needs you groups. The Needs you model has no
such groups: `NEEDS_REASONS` is the four above. Duplicates and invite requests live on `/admin/organisers` (the
`DuplicatesAlert` and `InviteRequests` panels, not part of this PR), and a failed invite shows on its Organisers row
("The last send failed. You can send it again." + Send invite again), walked in `organisers-status-*`.

## Findings and fixes (each red first in `4ced91b`, fixed in the next commit)

| # | Screen / shape | Finding | Fix |
|---|---|---|---|
| F1 | Organisers / every shape with rows | The organiser name link (the way into each row's page) was a 17 px tall tap target (34 px when it wrapped). | Link is `flex min-h-[44px] items-center`. |
| F2 | Needs you tab and the `/admin/organisers` entry / any count | The count badge was white on the destructive token `#ef4444` at 10 px: **3.76:1**, under AA. | One shared `BADGE` class in `frontDoorUi.ts`: white on red-700 (6.5:1). Global token untouched. |
| F3 | Organisers / Invited x none, Invited x skipped | The disabled Send reason said "Switch Run by us off ..." on rows whose switch was already off: copy pointing at a control in the other state. Also red in a new table-driven unit case (`frontDoor.models.test.ts`, chip x status). | `sendControl`: none on an off row says "Switch Run by us on, then off again, to prepare one; it needs their email." (the switch-off path is what prepares an invite, `runByUsMessage`); skipped says "on, then off" or "off and on" by the switch's state. |
| F4 | Organisers / long names | Found by LOOKING at the screenshot: a 70-character unbroken name ran under the chip and was cut off (the F1 flex link made the text a min-content flex item). A "no text wider than its box" check was added and went red, then: | The name sits in its own `min-w-0 break-words` span inside the link; it wraps. |

Seen and left as is (not defects of this PR, said here so nobody re-finds them):
- The "Your dancer profile is missing" banner on every shot: the fake's signed-in user has no dancer profile. A real
  admin with a profile does not see it.
- A sticky header painted mid-page in a few full-page shots (`add-untouched-360`, `organisers-answers`): Playwright's
  full-page capture of a sticky header after scrolling, not the layout.
- `entry-badge`: "The duplicate check did not load" on `/admin/organisers`: the fake does not answer the duplicates
  RPC. That panel is not in this PR.
- The switches are native checkboxes with `role="switch"`; they look like checkboxes. Owner's call if they should
  look like toggles.
- A Needs you item with no organiser (`quiet_30_days`, `organiser_id` null) shows only its label, no action. No prod
  row has this shape today.
- A run-by-us row with a queued, sent or failed invite renders sensibly (Send on/off by status), though the server
  may never produce it.

## Not verified

- **Fake data, not the real RPCs.** Every answer is scripted from the shapes `frontDoorApi.ts` parses and the admin
  contract it was written against (admin PR #1007). If the live RPCs send another shape, these screens were not
  shown it. The prod shapes are copied from the owner's phone screenshots, not read from the database (the brief
  forbids touching it).
- **Real data was seen only on the owner's phone, on 3 screens** (Organisers list, Needs you, Add), before these
  fixes. The fixes (F1 to F4) have not been seen on real data or on a real phone.
- Send / Run by us / Approve were walked with their refusals and one success each, not every server code on a
  real round trip; the list's refresh after a write is not walked against a changing server.
- Chromium with phone emulation, not Safari on iOS; no safe-area inset.
