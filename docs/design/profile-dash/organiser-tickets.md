## The money rule (PR #1541, branch `claude/ticket-money-visible` @ 59e0809, NOT merged yet)

One function in `core.js` (`showMoney`): **amounts show only when the seat is owner AND the server's
`money_visible` is not false**, exactly the PR's gate (`TicketsEntry.tsx:164-166` @59e). Every money-shaped
thing reads it: takings tile, per-ticket "taken", order amounts, buyer first name (`orderTitleFor`, else
`Order CODE`, `ticketModel.ts:619-620` @59e), Refund buttons, Payouts, guest-list names, CSV.

| Role x money_visible | Shape | What they see | Why line (one per cause) |
|---|---|---|---|
| Owner, true | `normal` | Amounts, names, Refund, Payouts | none |
| Owner, **false** | `ownerhidden` | Counts only, `Order CODE`, no Refund, Payouts row says "Hidden while amounts are off" | "Amounts are hidden because the server did not confirm money access for your seat. Counts below are right. Reload; if it stays, contact support. Refunds are off until then." (fixes inventory GAP 3: today the owner gets no reason) |
| Manager, false (server) or null (role) | `manager`, `guestsmgr`, `pricereq` | Counts, `Order CODE`, prices (public anyway), can add / pause; price change goes to the owner | `COUNTS_ONLY_NOTE` (`ticketModel.ts:76`) + "You can add and pause tickets; a price change goes to the owner to approve." Orders foot: `NOT_OWNER_REFUND` |
| Contributor | `contributor` | Counts, view-only rows (not tappable), no Add | "You can look, but not change tickets. Amounts and refunds are for owners. Ask an owner (Sam Sample) ..." |
| Anyone, loading | `loading` | Skeleton; no amount is drawn before the server answers; Add disabled with reason | "Add a ticket works once your tickets have loaded." |

Refund `not_allowed` (server refuses even though the screen offered Refund): `refunddenied` says
"Nothing was refunded", names the reason, uses `NOT_OWNER_REFUND`, offers Reload.

## The two layout ideas

| | **A: one page per event** | **B: Sell / Orders / Money** |
|---|---|---|
| Top | Event picker card ("Change") | Same picker, then a 3-way switch |
| Numbers | 3 tiles: sold of capacity, taken after refunds (owner) or orders (others), checked in | Same tiles, on Sell |
| Tickets | Card list, sold bar, state tag, then Add a ticket | Same, under Sell |
| Orders | "Latest orders" (5) + See all, Refund per row, then Guest list button | Orders part: Guest list button first, then all orders |
| Money | "Money" heading at the end: Payouts row (owner) or reason row | Money part (owner): taken, refunded, Payouts. For others the Money button is **disabled with the reason under the switch** |
| Long event (12 tickets) | One long scroll; orders start far down | Sell stays short; orders one tap away |
| Build cost | Lower: today's `TicketsEntry.tsx` is already one scroll | Higher: new part state + deep links |

**Why A (plain English):** everything about one night is on one page, so an organiser at the door can glance
down and see sold, money and who is in without learning where things live. Today's screen already works this
way, so it is the smaller change. Its cost: with many tickets, orders and payouts sit a long scroll down.

**Why B (plain English):** the three jobs on this tab are different (set up what you sell, deal with people
who bought, see the money), and B gives each its own short page. Money being one button that is visibly off for
managers makes the money rule obvious instead of quietly missing. Its cost: one more tap, and the guest list is
behind Orders.

## Careful lane (admin repo; needed before either option ships as drawn)

1. **`money_visible` from the server.** Neither `ticket_sales_summary_v1` nor `_v2` emits it in prod (0/2).
   Until it does, PR #1541's gate treats null as "not false", so it is a role gate only. Also make the client
   wait for the summary before any money read (inventory GAP 2: today `showMoney` is true while loading).
2. **Server-side owner approval for prices.** `ticket_type_upsert_v1` and `ticket_price_step_set_v1` have no
   owner test in their source; a manager can change a price server-side. Needs: price changes owner-only, plus
   a new "price change request" table + RPCs (create, list for owner, approve, decline) and a notice to the owner.
3. **Refund stays owner-only server-side** (`not_allowed`, Part B) and gains a stored reason (none today,
   ticketsApi.ts:283-285) and an audit row (who approved, when, amount).
4. **Payouts read.** A server read of payout status (`payouts_enabled`, restricted, next payout) for the owner
   only; nothing in the DB holds payouts today. Bank / schedule changes stay in Stripe.
5. **Guest list per ticket for managers**: a counts-and-codes read with no `buyer_name` (as PR #1541's
   `ORDER_SELECT_COUNTS`), and the CSV must drop full names (inventory GAP 9) or be owner-only.
6. **Promo codes**: role check (none today, promoModel.ts:9-10) and hide discount £ from managers (PromoSection.tsx:197).
7. **Contributor read access** to Tickets (today home_v1 excludes those pages, TicketsEntry.tsx:89): an ACL decision.
8. **"Part refunded" status** derived from `refunded_pence` (column exists; tag is a client change only).

## Recommendation: not picked for the owner

Lean: **Option A**, because 95% of use is on a phone at or near the event, prod events have 3-4 tickets and a
handful of orders, and A is a reorder of today's screen, which keeps the money-area build small and testable.
B is the better choice if the owner wants the money rule to be visible (a switched-off Money button) and
expects events with 10+ ticket types. The owner decides.

**Alternatives rejected:** (1) a money table with a column per role: cramped at 390px and shows managers a
column of blanks; (2) refunds by swipe: too easy for an irreversible money action; (3) a separate Payouts tab:
Stripe owns payouts, so it would be a near-empty tab; (4) letting managers refund small amounts: conflicts
with PR #1541 Part B (`not_allowed`).
