# Design record: P3 W2d sessions and line-up (PR #1068)

Flag: `organiserP3` (OFF). Branch `claude/p3-w2d-sessions-lineup`. Brief: `brief/p3-w2d-sessions-lineup`.

## Brief
- **Who:** an organiser on a phone (390x844), on their P3 event page.
- **One job:** change a session (name, times, room, level, line-up) for every date or for one date, add one, take one off.
- **Feel:** the C3 sheets: one sheet per step, plain words, every greyed control says why.

## Review round 1 (`docs/reviews/1068-r1.md`, fixed on this branch)

Every fix has a test that was run red against the unfixed code first (`sessions.send.test.tsx`, `sessions.data.test.ts`), then green.

| # | Finding | Fixed? | How / why |
|---|---|---|---|
| 1 | Typing in "Just this date" lost on a background refetch | Fixed | The edit state is keyed on the STORED version (the date programme's `version`, or `ws.series.version`) and the draft id, not `dataUpdatedAt`. A refetch of the same version keeps the typing; a new version (another save) starts again from what is stored. |
| 2 | A NEW nameless session saved on Every date, refused on Just this date | Fixed | A NEW session needs a name in both scopes: "Give this session a name." under a disabled "Add this session" (the empty form included). `problemsOf` no longer drops the title problem; a STORED untitled item still passes because `validateTree` checks a name only when it changes (#25). Matrix: new/stored x titled/untitled x scope (10 cases). |
| 3 | Idempotency key outlives its version | Fixed | Read on prod (SELECT only, 2026-10-27): `apply_aggregate_write_p5` looks a key up in `command_idempotency_p5` by (actor, key) ALONE and replays the stored answer whatever the envelope; it stores a row only on success (a refusal raises and rolls back). So a reused key after a refusal is harmless today, but a key reused at a new version could replay an OLD success (for example, the same tree saved again after a dropped-but-landed write and a change in between). The key is now per (version, command), and dropped after any non-network failure. A pure retry (same envelope after a dropped connection) keeps it (existing test). Tests: a refusal then a tap gives a fresh key; a reload at a new version gives a fresh key and the new `expected_version`. |
| 4 | Re-adding a taken-off stored person from the search | Fixed | The result row is disabled: "Taken off above. Tap "Keep them on" to put them back." (the button's real label; "Put back" is not on screen). |
| 5 | Performance line-up: Teacher/DJ toggle with no explanation | Fixed | One line from `whyCannotAddPerson` (its one copy): "Performers and the MC are added by the Bachata Calendar team." |
| 6 | Remove-from-every-date confirm does not warn up front; "all 0 dates" | Fixed | `CHANGED_SESSION_REMOVE_CONFIRM` shows in the confirm; `removeAllBody(0)` reads "It comes off the programme." |
| 7 | Switching scope silently drops typing | Fixed (the simpler way) | Switching still starts again from that scope's stored session; once something is typed, a line under the picker says so: "Changing which dates clears what you typed here." |
| 8 | Series caps refused with "Reload the page" | Fixed | Three anchored COMMAND_COPY rows before the loose set_program rule, texts read on prod (`_owner_program_problem_p5`): 60 sessions, 20 people a session, 300 line-up places, each saying what to take off. Refusal-copy phone spec green (4/4). |
