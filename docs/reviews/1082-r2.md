## Findings (most severe first)

### 1. After a refused stale save, "Start again" then the same edit can never save: the held attempt keeps its OLD version and key (blocks merge: it breaks the very path r1 #1 made the only way forward) — CONFIRMED by trace
- `EditTray.tsx` `useSaveRun.run` (`held.current` is cleared only on success, line ~87); `saveModel.ts` `attemptFor` returns the held attempt whenever `sig` (JSON of the plan) is unchanged and `done < steps.length`; `version` passed in is ignored then. `form.restart` (`EditTray.tsx:~37`) only resets the form; nothing clears `held`.
- Failing input: open Details at v5, change description to "X". Someone else changes the ticket link (v6, name unchanged). Tap Save: sent at `expected_version 5`, server answers `version_conflict`. Tap "Start again": base/draft become v6 data and `opened.version` 6. Retype description "X": the plan is byte-identical (`upsert{name, default_description:"X"}`), so `attemptFor` hands back the held attempt, step 0 still has version 5 and the same key. Refused again, every time, until the person edits something else or reloads. Same on Prices (plan `{name: ws.series.name, ...}` is identical when the other person did not rename).
- Server side note: a refused call leaves no idempotency row, so the key is not the problem; the pinned version is.
- Fix: drop `held` on a `version_conflict` (or when `restart` runs), or include the version in `sig`.

### 3. A brief "someone else saved" banner still appears between step 1 landing and the workspace refetch (nit) — CONFIRMED by trace
- `EditTray.tsx` `landed()` sets `opened.version = 6` immediately; `ws.series.version` is still 5 until the reload that `useSendOnce` started finishes. `changedElsewhere(6, 5, own={6})` = `5 !== 6 && !own.has(5)` = true, so the banner (and its "Start again", which drops unsaved typing such as the chat link) shows during step 2's network time. It clears once the refetch lands. r1 #4 is fixed in the end state, not during the window. Fix: compare against `max(ws version, own)` or treat `now < openedAt` as not-elsewhere.

### 5. (a) Stale typing overwriting newer data — fixed as far as the server goes; copy/recovery blocked by #1 — CONFIRMED (server)
- `_cmd_series_upsert_p5` itself has no version check; it is in `apply_aggregate_write_p5`, which raises `version_conflict: expected %, got %` (three sites) and sits AFTER the idempotency replay return. Sending the opened version therefore does refuse a stale save, and an unchanged `name` is the opened one, so a stale save cannot revert a rename. Note the prices builders send `ws.series.name` (the LIVE name) with the opened version: harmless, because a rename bumps the version and the save is refused.
- Whether the refusal reads as plain copy was not traced (`COMMAND_COPY` for `version_conflict` not read). "Start again" itself works for the form (see #1 for the retry).

### 6. (b) SessionSheet reusing the same key — checked, no collision — CONFIRMED
- `sessions.ts useEverySend`: the key map id is `${version}|${JSON.stringify(command)}`, so a re-save after more typing is a different payload and gets a NEW key; the same key is only reused for the identical command at the identical version. The server's replay lookup is `(actor_id, idempotency_key)` only: no request hash is compared (a replayed key with a DIFFERENT body would return the stored success and write nothing). The client never does that today, but that guarantee is client-only; worth a line in the design record. The date path (`sendDate(began ?? prog.data.version, ...)`) was only read, its key handling is outside this diff.

### 7. (d) Place-city lookup — no hang found, fast tap cannot win (nit-level residue) — CONFIRMED for the Save race, PLAUSIBLE for the hang
- `DetailsScreen.tsx useVenueCity`: `problem` is `detailsCityBusy` until `found` matches the picked venue, and `saveButton` disables Save when a problem is named, so a tap cannot beat the lookup; `plan` is rebuilt from `city.id` each render. Switching A to B to A re-looks-up A. Failure shows copy plus "Try again" and holds Save. A hang is only possible if `resolveCanonicalCity` never settles (no timeout seen in this diff; not checked in the resolver): then Save stays held on "Finding the place's city" with no retry button (retry shows only on `failed`). PLAUSIBLE.
