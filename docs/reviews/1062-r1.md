### 2. FIX BEFORE ARC END: "Put this week back" is enabled at the date cap, the server refuses it -- CONFIRMED
- **Where:** `src/modules/organiser/p3/model/dates.ts:93`
  (`if (d.state === 'skip') return [row('unskip', base ?? (d.ruleDate ? null : DATE_WHY.unskipOffRule))]`).
- **What is wrong:** `_cmd_series_unskip_date_p5` revokes the tombstone and then DELEGATES to
  `_cmd_series_add_date_p5`, whose date cap refuses a non-admin when the series already has 30 or more
  upcoming scheduled dates and the date is not stored (`permission_denied: date_cap: ...`). The rule set
  applies the cap to Add (`addDateWhy`, line 124) and to Bring it back (line 99) but not to unskip, so the
  break sheet's one row is enabled and the tap fails. (The refusal does read as copy: `COMMAND_COPY`'s
  `date_cap` rule.)
- **Concrete failing input:** `SeriesFacts{kind:'weekly', lifecycle:'live', upcoming:30}` and a break on the
  cadence from today on. Prod today: 1 live/paused series holds 30+ upcoming scheduled dates AND an upcoming
  tombstone, so a real organiser meets this.
- **Fix:** `row('unskip', base ?? (!d.ruleDate ? DATE_WHY.unskipOffRule : s.upcoming >= DATE_CAP ? DATE_WHY.cap : null))`
  plus the matrix row.

### 3. FIX BEFORE ARC END: "Change the time" is greyed where the server allows it, and allowed where it may refuse -- CONFIRMED (grey arm) / PLAUSIBLE (refuse arm)
- **Where:** `src/modules/organiser/p3/model/dates.ts:104`
  (`s.hasSessions ? null : DATE_WHY.noSessions`); `hasSessions` = `programHasSessions(series.program)`
  (`shared/seriesModel.ts:68`), i.e. the series programme has items.
- **What is wrong (grey arm):** `_cmd_occurrence_set_time_p5` (D8) does NOT refuse a series with no programme
  times: when `v_has_program_time` is false and the date has no sessions it CREATES the date's own date-time
  session (`date_session_created: true`) and returns. The client greys the row with "This date has no session
  times to move yet. Add a session first." Greyed-but-allowed, and the copy points at a control that P3 does
  not have (sessions are W2d).
- **What is wrong (refuse arm):** the handler's refusal `no_sessions_for_time_override` fires when the series
  HAS programme times but this date's effective session set is empty (every programme item cancelled on
  this date, no added session). `hasSessions` is series-wide, so the row is enabled and the send is refused.
  Copy exists (`^no_sessions_for_time_override`), so the user sees "Ask the Bachata Calendar team to set up
  the class times" on a series that has them.
- **Concrete failing input (grey arm):** a live recurring series whose programme has no timed item, a coming
  date. Prod today: 0 live/paused recurring series with a coming date and no programme time, so no live
  user is blocked right now; the shape is the ADR-016 "occasional" one the handler was written for.
- **Fix:** grey on `!hasSessions` only when the series has programme times but this date has none (needs the
  per-date session facts; until W2d lands, drop the grey and let the D8 arm run), and keep the refusal copy.

### 4. FIX BEFORE ARC END: a festival's date cannot be cancelled in P3, though the server allows it -- CONFIRMED (code) / PLAUSIBLE (intent)
- **Where:** `src/modules/organiser/p3/model/dates.ts:101`
  (`row('cancel', base ?? (fest ? DATE_WHY.festivalCancel : null))`).
- **What is wrong:** `_cmd_occurrence_cancel_p5` has no format rule, and the dispatcher's owner gates on
  `occurrence.cancel` are past-date and ended-series only (read: `apply_aggregate_write_p5` lines 643-650,
  891-896). The brief and the design record name `set_time` and `move_date` as the festival refusals; cancel

- **Concrete failing input:** `SeriesFacts{kind:'festival', lifecycle:'live'}`, a coming scheduled date.
  Prod today: 6 live/paused festivals with a coming date.
- **Fix:** enable `cancel` on a festival (the server takes it), or record the owner call that festivals are
  admin-cancelled in `docs/design/1062.md`'s table (it is not there now).

### 5. FIX BEFORE ARC END: a recurring series with no stored rule tags EVERY date "Not the usual day" -- CONFIRMED
- **Where:** `src/modules/organiser/p3/model/dates.ts:148` (`(kind === 'weekly' || kind === 'course') && !d.ruleDate`),

- **Concrete failing input:** `series{format:'recurring', recurrence_rule:null}` with three coming dates.
  Prod today: 2 live/paused recurring series with a null rule and coming dates.
- **Fix:** treat a rule-less recurring series like `custom` in `dateMarks` and in the skip reason
  (`DATE_WHY.noPattern`), or derive `ruleDate` as "not applicable" when there is no rule.

### 6. FIX BEFORE ARC END (copy): All dates empty states point at controls that are greyed -- CONFIRMED

### 7. NIT: "a retry is the same write" holds only when the first attempt did not commit -- CONFIRMED
- **Where:** `src/modules/organiser/p3/data/dates.ts:216-228` (`KeyRing` keyed on `JSON.stringify(plan)`,
  which includes the date `version`) and `:267-275` (`useSendPlan`'s `finally` invalidates the workspace on
  every outcome).
- **What is wrong:** after a dropped response (the server committed, the client saw a network error) the
  invalidation refetches the workspace, the date's `version` moves, the plan's JSON changes and the retry
  gets NEW keys, so it is a second command rather than the idempotent replay the comment promises. The
  effect is benign for cancel / details / time (same end state) but the sheet misleads: a committed skip makes
  `StoredDate` return null (`DateSheet.tsx:354`) so the sheet vanishes under the error with no toast; a
  committed move greys the button as "already has a date on that day" under the error.
- **Fix:** key the ring on the command list without the version (or on the plan's `occurrenceId` + commands),
  and let the replay (which runs BEFORE the version check: `apply_aggregate_write_p5` line 550-554) answer.

### 8. NIT: the composite's second refusal has no copy and leaves half the change applied -- PLAUSIBLE
- **Where:** `src/modules/organiser/p3/data/dates.ts:134-144` (`resetNormalPlan`: `set_override` nulls, then
  `set_time {reset:true}`); `shared/selfServeErrors.ts` has no rule for
  `invalid_payload: date_time_session_has_people`.
- **What is wrong:** `_cmd_occurrence_set_time_p5`'s STP1 arm refuses a reset that would drop a date-time
  session carrying people. When the override call has succeeded and the reset is refused, the details are
  already back to usual, the time is not, and the user reads "Something went wrong. Please try again."
  (GENERIC). A retry sends the reset alone (the plan changed) and fails the same way.
- **Fix:** a `COMMAND_COPY` row for `date_time_session_has_people` ("This date's own time holds people on its
  session...") and, on a second-step failure, a toast that says the details went back and the time did not.

### 9. NIT: "Skip this week" on a booked date is enabled and refused -- PLAUSIBLE

### 10. NIT: upcoming breaks on a non-weekly series are invisible -- CONFIRMED
