## 3. Key compatibility (r1 finding 3)

- The proposed key `<uuid36>-<uuid36|default>-<16hex>-wf1-960x1200.jpg` is about 108 characters, all `[0-9a-z-x.]`. It is URL-safe, and R2 and Supabase storage accept it.
- `HEALTHY_BAKED_KEY_RE` (`scripts/check-og-images.mjs:407`) is anchored and ends `(?:-[0-9a-f]{12})?[.]jpg$`, so it reds the new key. That is expected and D9(3) covers it. Suggested shape: `(?:-[0-9a-f]{12}|-wf[0-9]+-[0-9]{3,4}x[0-9]{3,4})?[.]jpg$`. These are mutually exclusive, which matches D8: facts are not in a wf key.
- Other parsers in this repo: `BAKED_OBJECT_RE` (`check-og-images.mjs:395`) takes the last path segment and is compatible. `app/sameHostImage.ts` reads only the host, so it is compatible. The fixtures in `app/ogImageHost.test.ts:16-18`, `tests/ogFactsTagFlagOn.test.ts` and `tests/ogBakeDegradeRefusal.test.ts` build or assert key shapes and must be updated in B1. `scripts/backfill-og-images.mjs` does not parse keys. The admin repo was not readable. In prod SQL, the trigger comment says "image_url is sha1 of the COVER url", which is a comment, not a parser.

## VERDICT: BLOCK

N1 is a state the brief asked about, and it is reachable on every flip, every rollback and every deploy skew: the page declares one size while the same live URL returns the other layout's pixels from a crawler, browser or edge cache. The fix is contract-only and needs no SQL (D10 holds): the layout goes in the live URL. With N1 applied, and N2-N10 written in, the contract can pass. Under the two-round rule this goes back to the lead rather than to a third review, unless the lead judges the N1 change big enough to need one.
