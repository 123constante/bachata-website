# Review r1 of PR #1068 (P3 W2d Sessions and line-up)

Head reviewed: `c60588e` (`claude/p3-w2d-sessions-lineup`) against `main` `0f52b65`. Read-only: prod function bodies read via SELECT, nothing run, no tests executed. Reviewer did not build it.

## Findings (most severe first)

### 1. Typed edits in "Just this date" are silently thrown away when the date's programme refetches
- `src/modules/organiser/p3/screens/SessionSheet.tsx` (`baseKey`, `form = edit && edit.k === baseKey ? edit.f : base`)
- `baseKey` includes `prog.dataUpdatedAt`. App default is `refetchOnWindowFocus: true`, `staleTime: 60_000` (`src/App.tsx`), and `useDateProgramme` overrides neither. Any refetch (focus, or the `reload()` that follows a save or a `reload`-type refusal) changes the key, so `form` snaps back to `base`.
- Failing input: on a phone, open a date's session, type a new name and times, switch to Instagram or the calendar for over a minute, come back. The query refetches, the key changes, the fields revert, and Save shows "Nothing changed yet" with no message.
- Severity: fix before arc end. CONFIRMED by code reading (not run). No stored data is lost; the user's typing is.

### 2. A new unnamed session saves on "Every date" but is refused on "Just this date" (answer to brief point 4)
- `src/modules/organiser/p3/data/sessions.ts:99-108` (`problemsOf`) drops the `title` problem for any item whose trimmed title is empty. That is right for stored untitled items (the #25 shape) but it also covers a NEW item, because `validateTree` flags `!o` items and the filter does not tell new from stored.
- The client can therefore send `title: ''` for a new item. Server: `_owner_program_problem_p5` only requires `title` to be a string (`_self_serve_text_problem_p5('')` returns NULL). `_cmd_series_set_program_p5` inserts `v_item_elem->>'title'` as is, and `event_series_program_item_p5` has no CHECK constraint. So the server ACCEPTS it. The PR's "unproven on prod" case is: it is accepted and creates a nameless session on every future date.
- On "Just this date" the same input is refused: `titleProblem` gives "Give this session a name." and the writer says "title is required" (`organiser_set_occurrence_programme_v1`). Two scopes disagree.
- Related: "Add this session" is enabled on a fully empty form in both scopes (`dirty = true` for a new one).
- Failing input: Add a session, leave the name and times empty, tap "Add this session" under Every date. A nameless, timeless "Class" row appears on every date.
- Severity: fix before arc end. Pick one rule. I suggest requiring a name for NEW sessions in both scopes and keeping the #25 leniency for stored items only. CONFIRMED.

### 3. Idempotency key outlives the version it was sent with (PLAUSIBLE)
- `data/sessions.ts:242-251` (`useEverySend`). The key is kept per `JSON.stringify(command)` until the call resolves. After a failure the workspace reloads, so the retry goes out with the same key and a NEW `expected_version`, and the same key stays attached after a definitive refusal.
- I did not read the server's idempotency handler, so I cannot say whether it replays the stored result or rejects a changed envelope.
- Failing input: tap Save, get `version_conflict`, the sheet reloads, tap Save again with the same tree. Same key, new version.
- Severity: fix before arc end, after checking the envelope handler. A retry after a dropped connection (the case the comment promises) is correct. The refusal case is the open one.

### 4. Line-up: removing then re-adding the same person on a date is blocked with confusing words
- `LineupSheet.tsx:47-48,92-96`. The result button is enabled for a stored person who is currently "taken off", so `add()` produces `origin:'added'` plus `origin:'stored', removed:true` for one id. `peopleProblem` (`shared/programmeModel.ts:451`) then refuses with "Someone is listed twice in this line-up. Undo the change and try again." The server rejects the same shape.
- Failing input: Just this date, take Ana off, search "Ana", tap her, Save. "Put back" exists, but the search result invites the action.
- Severity: nit. Disable the result row when the person is stored and removed, with "Use Put back".

### 5. Line-up for performance sessions: a Teacher/DJ toggle with no explanation
- `LineupSheet.tsx:32`. `addRoleFor('performance')` is null, so the picker defaults to Teacher and offers "Teacher/DJ". The old screen explained via `whyCannotAddPerson` ("Performers and the MC are added by the Bachata Calendar team") and the new sheet does not. Existing performers and the one `mc` row render read-only with "Set by the Bachata Calendar team", which is right. There is no performer search (`organiser_search_people_v1` has no such role), so there is nothing to wire; only the explanation is missing.
- Severity: nit.

### 6. Remove-from-every-date confirm does not warn about per-date changes up front
- `labels.ts:183-184` and `SessionSheet.tsx` removeAll step. `CHANGED_SESSION_REMOVE_CONFIRM` exists in `programmeSeriesModel.ts` for exactly this, but the new confirm does not use it. The server refusal (COMMAND_COPY, "only an admin can remove it") shows after "Yes, remove", in plain words, so nothing is lost; the person just learns after tapping. `removeAllBody(0)` would read "all 0 dates".
- Severity: nit.

### 7. Switching scope silently drops unsaved edits
- `baseKey` includes `scope`, so toggling Every date / Just this date resets the form. Nit.

### 8. Refusal copy for the series caps is misleading (PLAUSIBLE)
- `selfServeErrors.ts:160` sends every `series.set_program` shape refusal to "Reload the page, then make your change again". The server also refuses `holds at most 60 sessions`, `a session holds at most 20 people` and `300 line-up entries`, where reloading does not help. The client does not mirror these caps (it mirrors 40 / 20 / 12, which are the date writer's caps). Nit, rare.

## Checked and found aligned

1. **Every date.** `buildDays` sends the whole tree with every stored id and untouched field echoed; `ws.series.version` goes in as `expected_version` through `useSendOnce`; an untouched tree builds `null` and sends nothing. The gate is `AW1_APPLIED` through `factsOf`; no second gate. Compared with `_owner_program_problem_p5` and `_cmd_series_set_program_p5`: key allowlists, pair rule (`teacher:mc` etc. are echoed, not offered), 200-char title (client 120, stricter), HH:MM, `level_keys` and the festival `days>1` refusal all match what the client builds. Only gap: a non-festival series with more than one stored day is refused by the server (`_organiser_festival_program_ok_v1`) but not greyed (PLAUSIBLE, not traced; rare).
2. **Just this date.** `buildPayload` sends the COMPLETE date programme; `people_add` / `people_remove` are per session against `prog.data.version`. Server refusals (cancelled, past `< today` London, multi-day or festival, ended or archived) match `scopeWhy` / `NOT_EDITABLE`; each is greyed with a reason, and "loading" greys until the reader answers. `type` and room stay out of per-date saves (server: type admin-only).
3. **Data loss.** A stale read cannot overwrite silently: every-date uses `expected_version`, per-date uses the programme version, and a `reload`-type refusal reloads. Removing an item with per-date overrides is refused by the server and mapped to plain copy (`COMMAND_COPY`). An untouched save is disabled and sends nothing (`dirty`, `isDirty`, `treeDirty`).
5. **Line-up.** Search is `organiser_search_people_v1` via `searchPeople` (min 2 chars); performers and `mc` read-only; removeall wording is in plain words with a confirm step and a "Keep it" button.
6. **Festivals / mapping.** Festival is read-only with `L.festivalAsk` ("Ask us"); kind comes from `KindChips` over the shared `SESSION_TYPES` / `TYPE_LABEL` (stored kind outside the four shows pressed and disabled); one `levelLabel` map exported from `data/eventPage.ts`; `roleWord` shared.
7. **Copy.** British English, full weekday names via `fullDate`, `’` / `&rsaquo;` escapes, no new Unicode punctuation seen. Empty states carry an action. Controls not on screen are not named (`shownControls`).
8. **Flag-OFF.** P3 is reached only through the lazy `P3Routes` chunk (`AnimatedRoutes.tsx:51`). The diff is W2d files plus `shared/selfServeErrors.ts` (two additive rules). The 36 PNGs are all new files under `docs/handover/p3-w2d-sessions/`; none rewritten. The two new COMMAND_COPY rules are shared with old `/account/o` flows but only change copy for `series.set_program` refusals that previously fell through to the default.
