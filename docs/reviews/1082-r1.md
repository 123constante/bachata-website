# Review round 1: PR #1082 (P3 W3a Name and details + Prices)

Head reviewed: `4da101f` (`claude/p3-w3a-details`) against `main` (dd8112f). Read-only. Server read with `pg_get_functiondef` (SELECT only): `_cmd_series_set_group_chat_p5`, `check_owner_command_allowlist_v1`, the permission block and insert arm of `_cmd_series_upsert_p5`.

## Findings (most severe first)

### 1. Save sends the CURRENT version, not the version the screen opened with; Details also always sends the opened-time `name` (fix before arc end; arguably blocks merge) — CONFIRMED
- `DetailsScreen.tsx:62` and `PricesScreen.tsx:52`: `save.run(plan, ws.series.version)`. `ws` is the live workspace; the screen's own opened version is `useEditForm().opened.version` (`EditTray.tsx:23`), which is never passed.
- Failing input: open Details at v5 and change the description. Someone else saves (v6, e.g. renames the event). `ws` refetches to v6; the "someone else saved" banner shows (nit A working as designed) but the person taps Save anyway. The upsert goes against `expected_version: 6`, so the optimistic-lock check passes and the write lands on top of data the person never saw. Because `detailsPlan` (`details.ts:147`) always sends `name: draft.name.trim()` (the opened-time name), the other person's rename is silently reverted to the old name. Prices sends `ws.series.name` (current), so it does not revert the name, but the same stale-base/current-version mismatch applies to the fields it sends.
- Same shape for a retry after a failure: `attemptFor` keeps the held version only while the plan signature is unchanged; one more keystroke makes a new attempt against the then-current version.
- Fix: pass `form.opened.version` (expose it) to `run`; send `name` only when it changed, or when it is needed take it from the opened base and let a stale version refuse. A stale version then returns `version_conflict` and the banner/"Start again" is the only way forward, which is what nit A says.
- Does an untouched save send nothing? Yes: `detailsPlan`/`pricesPlan` return `[]`, `run([])` returns without a call. A one-field edit sends `name` + that field only (apart from the name issue above). Confirmed no other field (prices, passes, music, venue, chat) is added.

### 2. Prices: a "changed" list that builds to no command leaves a live Save that silently does nothing (fix before arc end) — CONFIRMED
- `prices.ts:35,60-64`: the `rows` spec compares with `sameValue` (JSON of raw rows; only top-level strings are trimmed), but `pricesCommand` compares the trimmed/`Number()`-normalised `toPass` output (`seriesExtras.ts:138-148`) and returns null when equal.
- Failing input: on an owner-shaped list, type a trailing space in a price name, or change `15` to `15.0` or `015`. Tray says "Not saved yet · 1 change", Save is enabled (`blocker` null), the leave guard is armed, but `pricesPlan` returns `[]`, `run([])` returns `ok:false` with no error and no toast. The person is stuck with a dirty screen and no message. Same for `methods` on a festival whose stored `door` is dropped by `toSend` (the spec says changed, `paymentChanged` says not).
- Fix: make the spec `same` use the same normalisation as the builder (`toPass`), and for methods compare via `paymentChanged`; or show "Nothing to save" when the plan is empty.

### 3. Venue change can leave the previous venue's city behind (fix before arc end) — CONFIRMED (client); server acceptance of an explicit null PLAUSIBLE
- `details.ts:138-141`: `if (cityId) payload.default_city_id = cityId`. `venueOverride.ts` (the function it calls) says a city that cannot be resolved must be sent as null "rather than leaving the old venue's city behind". `DetailsScreen.tsx:59` also swallows a resolver error to null. Failing input: change to a venue whose `city_name` has no resolvable city (or a transient resolve error): the series gets the new venue and keeps the old `default_city_id`. The old area (`Details.tsx:142-144`) passes the resolved city (null included) to `venueCommand`.
- Fix: send `default_city_id: cityId` (null included) when the venue changes, and tell the person if the lookup failed instead of swallowing it. Check the handler takes null for that key before relying on it.

### 4. A two-step save (upsert, then `series.set_group_chat`) shows a false "someone else saved" banner after step 1 lands (nit) — CONFIRMED by trace
- `EditTray.tsx:40-42,66-72`: `own` only records the final version (`saved()` runs only when every step succeeded). If step 2 (chat) fails, step 1 already bumped the version; `changedElsewhere(opened, now, own)` is true, so the banner tells the person someone else saved, and "Start again" would drop their unsaved chat link. Retry itself is correct (held attempt, `done=1`, step 2 reuses its key and the landed version).
- Fix: record each landed step's version in `own` as it lands.

### 5. Festival with a stored `free` code: price list hidden with no control to undo it (nit) — PLAUSIBLE
- `PricesScreen.tsx:45,63,71`: `free` is read from draft methods, the switch only shows when `choices.length > 1` (not on a festival). A festival whose stored `payment_methods` contains `free` hides the price rows and offers no switch. Not checked whether any prod festival has it.

### 6. Parity differences with the old area (nit / note) — CONFIRMED by reading
- Old `Details.tsx:38` caps: music 300 chars, tickets 500, Instagram 300 (`maxLength`). P3 has no per-field `maxLength`; the only bound is the server's 2048 for links. Not a data risk, but the rules differ.
- Link rules, video cap (`MAX_VIDEOS`), description cap and the profile/ended/archived locks are called, not copied. Good. `instagramToSend` and `chatProblem` are new P3 logic with no old-area twin (chat is new; Instagram handle to URL conversion is P3-only, the old area sent what was typed).
- Prices has no profile lock; the old `PaymentEdit.tsx` has none either (checked), so this matches.

### 7. Cover upload control (nit) — CONFIRMED
- `DetailsScreen.tsx:125-127`: a real `<label for>` + native `<input type=file>` with `p3-in`, so it is labelled, keyboard reachable and `min-height: var(--tap)`. The browser's own "Choose File / No file chosen" text stays unstyled (`p3.css:211`). Acceptable, but a styled button wrapping the input would match the rest of the area. Undo does not remove an already-uploaded file (orphan upload) or clear `photo.error`.
