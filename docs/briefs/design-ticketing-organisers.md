## 1. Owner decisions this design obeys (do not reopen)

## 2. Design: one concept, "price steps"
A ticket type keeps `price_pence` as its BASE price. Add a schedule of later steps:
`ticket_price_steps(id, ticket_type_id, effective_from timestamptz, price_pence int, created_by, created_at)`, at most 3 rows per type, `price_pence > 0`, unique (ticket_type_id, effective_from), `effective_from > now()` when written. EFFECTIVE price at instant t = the price of the latest step with `effective_from <= t`, else the base price. Early-bird, "last-minute" and a rise are all just steps. (Alternative rejected: editing `price_pence` by cron: late, not auditable, races with reserves.)
Orders store `unit_price_pence` per order LINE (`ticket_order_lines`, S1b), so buyers keep what they paid (Q9). The rule that blocks editing the base once orders exist stays; steps are the sanctioned way to change price after sales.

### 2b. Base price, free tickets and the paid invariant (F6, F11)
INVARIANT (write it in the T1 migration comment): for every type, `price_pence > 0` OR no step exists; and every step `price_pence > 0`. So "base > 0 iff every effective price > 0". Every free-ness check that reads the base (v1 free gate, `set_status` Stripe gate, `ticketSymbol`, `buyLabel`, `moveBlock`, `TicketsBlock` `promoOn`) stays right only while this holds; they are NOT changed.
Enforced by:
- `ticket_type_upsert_v1` (T1 edits it, same version, same signature): refuses `price_pence = 0` while any step exists, reason `has_price_steps`. Base edits while steps exist and no orders: allowed when > 0.
- Step writer refuses a free base: `not_paid_ticket`. Refuses a step price equal to the base or to the step immediately before it (same effective price, nothing changes): `same_price`.
- Website (T3): the price field on a type with steps says why 0 is not allowed ("Remove the price changes first; a ticket with price changes cannot be free.").

### 2c. Time (F8)
- Storage `timestamptz`; DB `TimeZone` is UTC, so NO SQL ever turns a step into a date or text. The server returns `next_price_at` as timestamptz; "price rises on <date>" is built ON THE CLIENT with `Intl.DateTimeFormat('en-GB', { timeZone: 'Europe/London', ... })`. A drop says "price changes on <date>" (OPEN-D6).
- Editor input is London wall-clock (`datetime-local`), converted with the existing `londonInputToIso` (`ticketModel.ts:360-369`). That helper does NOT refuse a non-existent time (`2027-03-28T01:30` -> 02:30 BST). New rule, client AND reason copy: refuse when `isoToLondonInput(londonInputToIso(v)) !== v`, reason `time_does_not_exist` ("This time does not exist in the UK, the clocks go forward. Pick another time."). AMBIGUOUS time (`2026-10-25T01:30` occurs twice): accepted and resolved to the LATER instant (GMT, `01:30Z`); the editor shows "01:30 GMT (after the clocks go back)" under the field. The server still checks only `effective_from > now()` on the instant.
- Server time only: every comparison uses `now()` (transaction start) in the writer and the reserve; the client never decides whether a step is live (OPEN-D3).
- Boundary: live when `effective_from <= now()`; movable/removable when `effective_from > now()`. At the exact instant the step is live AND frozen; no gap, no overlap. A reserve whose transaction started before the instant charges the old price, which is the price the buyer saw.

### 2d. Organiser actions
Add step (date+time picker in UK time, price), move step, remove step, only while `effective_from > now()` (for a move: the OLD and the NEW time); at most 3; each later than the previous. Reasons: `step_in_past`, `too_many_steps`, `not_paid_ticket`, `out_of_order`, `same_price`, `time_does_not_exist` (client), `reserve_not_ready` (s.3a).

### 3b. `price_changed` (F3, r2 N2)
- Request: each `p_lines` element carries `expected_unit_price_pence` (integer). The order total cannot ride in `p_lines`, so DECISION: `ticket_checkout_reserve_v5(<v4 args>, p_expected_total_pence int)` with NO default (a missing argument is a call error, not a silent skip).
- Missing expected price FAILS CLOSED, on EVERY type (stepped or not), so the rule cannot silently stop applying when a step is added later:
  - DB (v5, FIRST statement, before any lock or write): every element must have `jsonb_typeof(e->'expected_unit_price_pence') = 'number'` AND the number is integral (`(e->>'expected_unit_price_pence')::numeric = trunc((e->>'expected_unit_price_pence')::numeric)`) checked BEFORE any `::int` cast; `p_expected_total_pence IS NOT NULL`. Else `expected_price_required`. A JSON string `"1500"` or a float `1500.5` is therefore a refusal, never a cast error (500).
  - Edge (T2 v5 path; T2b every path): `Number.isInteger(x)` for every expected value from the request body before the RPC; else `expected_price_required` with no DB call (this is where a string or float `expected_total_pence` is caught, since the DB parameter is a typed int).
- **Two checkpoints in v5** (line numbers are prod v4's, J-11; v5 keeps v4's order otherwise):
  - **(a) Unit check**, ONCE after the line loop (v4 line 119; the seam runs inside the loop at 116) and before line 121, so it can list every stale line, and BEFORE the promo limiter (123-131), the code lock (145) and the refusal-row INSERT (186): any line with `expected_unit_price_pence <> seam(type, night)` refuses `price_changed`. So a stale unit takes no place, writes no `ticket_promo_checkout_refusals` row and does not count toward the promo limiter.
  - **(b) Total check** (r3 R3-1), AFTER v4 line 193 and the onboarding refusal (195-198) and BEFORE line 200 (the promo "supersede" UPDATE that sets `promo_use_released = true` on this person's earlier pending orders), 213-225 (capacity) and 228 (order INSERT). Every input of the fee is known at 193, so compute it there from `v_net`, `v_total_q` and `p_booking_fee_per_ticket_pence` (`CASE WHEN v_net = 0 THEN 0 ELSE ... END`, same as v4 line 210) and refuse `price_changed` when `p_expected_total_pence <> sum(unit x qty) - discount + fee`. Why before 200: a refusal is a `RETURN`, so the transaction commits; a check after the supersede would commit the release of the earlier pending order's promo use with no new order taking it (on a capped code a second buyer could take that use, then the first order is paid and `_ticket_promo_use_sync_v1` sets `promo_use_released := false` again: N+1 sales on an N-cap code, triggerable on purpose with a wrong `expected_total_pence`). A code refused at 186 still wins over a fee-only or discount-only drift (186 precedes 193), which is the existing behaviour.
- Fee rule (r2 N5): the server charges NO fee when the net is 0 (v3/v4, J-9; J-11 line 210). The Website (T4) uses the same rule on the post-discount amount: `fee = net > 0 ? BOOKING_FEE_PENCE x quantity : 0`, replacing `pv.appliedTotalPence + sum.feePence` (`TicketsBlock.tsx:207`), so a 100% code with a non-zero fee sends expected total 0 and matches. Today `BOOKING_FEE_PENCE = 0` (J-44), so nothing breaks before T4.
- Reply (same shape as v4's other refusals): `{ok:false, reason:'price_changed', lines:[{line:<index>, ticket_type_id, new_unit_price_pence}], new_total_pence}`; at checkpoint (a) only stale lines are listed; at (b) `lines` is empty; `new_total_pence` is always present. `expected_price_required` has no extra fields.
- Edge contract (admin repo): T2 adds the v5 path (passes `expected_unit_price_pence` per line and `p_expected_total_pence`; replies `price_changed` to the client unchanged) and KEEPS the v3/v4 paths; T2b removes them and refuses missing values before the DB (s.3a).
- Client contract (Website T4): basket wire as in s.3a. `REASON_COPY` gains `price_changed` ("The price changed while this page was open. New total: <total>. Check and pay again.") which re-renders the basket with the new prices and a confirm button; confirming resends with the NEW expected values. `expected_price_required` copy: "Please reload the page and try again." No grace period (Q5).

### 3d. Promo codes, rounding, fee (F4)
Discount is computed on the effective unit by the shared `_ticket_promo_unit_discount_v1` (floor), in preview and reserve alike, so equal unit means equal discount. A fixed code larger than a lowered step clamps to the unit and can make a line free; `below_minimum` (30p) can then appear after a step DOWN for a buyer whose preview passed; that buyer gets `price_changed` first at the unit check (s.3b checkpoint a), then sees the refusal on confirm. Fee: v3/v4 charge no fee on a zero net, and the Website must use the same rule (s.3b, r2 N5). Fee: page fee is a Website constant, server fee an env secret; a mismatch now fails as `price_changed` via `expected_total_pence` instead of charging an unseen amount. OPEN-D1 proposal stands (code applies as written to whatever price is effective).

### 3e. Stripe
Edge `buildCheckoutSessionParams` builds Checkout line items from the order lines' `unit_price_pence` / `discount_pence`, never from the ticket type (taken from the 2026-11-09 read for the single-type order; RE-VERIFY against the v4/v5 per-line edge code as part of the T2 G-1 proof). So steps need no Stripe change as long as the reserve writes the effective price into each line.

### 3f. Locks
v4/v5 lock types by id, then night counts, then the promo code row. The seam reads steps without locking. Step writers take ONLY the type row lock (`SELECT ... FROM ticket_types WHERE id = $1 FOR UPDATE`) first, so a step edit and a reserve on the same type serialize and no new deadlock cycle appears.

## 7. Open design decisions (none is a product question for the owner unless marked)
OPEN-D1 Fixed-amount promo codes across steps: discount applies as written to whatever price is effective. (Owner only if he wants codes tied to a step.)
OPEN-D2 Chain x steps: independent; steps are per type.
OPEN-D3 Time source: `now()` in the transaction, never the client clock (s.2c).
OPEN-D4 CLOSED by s.2c (non-existent time refused by round-trip check; ambiguous time = later instant, stated).
OPEN-D5 (BOUNDED, r2 F9/N6) A step during a pending order: the order keeps the price confirmed at reserve. v4/v5 set `hold_expires_at = now() + 15 min`; the Stripe Checkout session expires 32 min after it is created (`CHECKOUT_EXPIRES_AFTER_SECONDS = 32*60`, J-32), and the session is created by the edge right after the reserve. BOUND: a payment at a pre-step price can complete at most ~32 min after that order's reserve (plus the edge's own latency to create the session), and never for a reserve that started after the step (`now()` is the transaction start, s.2c). The 15-min hold bounds CAPACITY only, not price: a hold released at 15 min does not stop the session, so late payment after release is a NORMAL path. It is ACCEPTED: `ticket_order_mark_paid_v1` reopens the order at its stored line price, the buyer confirmed that price, and Stripe charged exactly `total_pence` (M-16, required). Hold release runs only through the `ticket-hold-sweep` edge, which has no pg_cron row (J-22): T2 must name its scheduler or add one (s.5 T2). If the sweep never runs, holds last until `ticket_orders_sweep_v1`, which changes capacity, not price.
OPEN-D6 Next price LOWER than current: show it ("price changes on <date>").
OPEN-D7 (PARKED, F5) Steps relative to each night.
