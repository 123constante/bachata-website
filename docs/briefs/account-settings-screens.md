Read first: CLAUDE.md in this repo, and any docs it points to on UI quality, phone QA, tests and deploy windows. Paste the PR's Phone QA section as the repo requires. You own only Website files; two admin workers own the database and edge functions (below). Never merge, never --no-verify.

## Goal
A signed-in person can, from their account: sign out, change email, download their data, disable (hide) their dancer profile reversibly, and, hidden behind several layers, erase the account permanently. Built against interfaces that are being merged in the admin repo in parallel: code and test against MOCKED responses with exactly these shapes (the typed Supabase client types may not know the RPCs yet: add a thin typed wrapper, do not edit the generated types file by hand if it is regenerated by a bot).

## Owner decisions (binding)
1. Two exits, Instagram-style: DISABLE (reversible: hidden from the public; sign in again and flip it back) is the easy one; ERASE is permanent and sits behind several layers: Account -> Settings -> Account ownership -> "Delete account" -> a screen listing what is lost + an offer to download the data first -> type DELETE -> confirm. Depth is a UX choice only: it must stay reachable without emailing support.
2. Erase is immediate after typing DELETE. No grace period.
3. Export is an instant JSON file download (client-side Blob from the RPC result), file name like bachata-calendar-my-data-YYYY-MM-DD.json.
4. A person who is the LAST owner of an organiser page cannot erase: show the reason and the blocking pages (names) with what to do (add another owner or remove the page). Disable stays allowed. An admin account cannot erase: show a short plain message.
5. Change email: Supabase `auth.updateUser({ email })`, standard confirm-both-addresses flow; show "check both inboxes" state; handle the not-confirmed-yet state.
6. Plain English, phone first (390x844), no jargon.

## Pinned interfaces (admin PR #792, being reviewed; RPC names and shapes are final)
- `my_account_export_v1()` -> { exported_at, email, profile|null, roles:{...}, ratings:[], attendance:[] }
- `my_profile_disable_v1(p_disabled boolean)` -> { disabled: boolean }. Errors (error.message is exactly the code): not_authenticated, invalid_argument, no_profile (the account has no dancer profile: hide the disable control with a reason).
- `my_account_erase_check_v1()` -> { can_erase: boolean, blockers: [{entity_id, name}], code: null | 'admin_account' | 'sole_organiser_owner' }
- Final erase is NOT an RPC call from the browser: it is the edge function `account-erase` (admin repo, being built in parallel; includes deleting photo files): `supabase.functions.invoke('account-erase', { body: { confirm: 'DELETE' } })` -> 200 { ok: true } | 409 { ok:false, code, blockers } | { ok:false, code:'media_delete_failed' } (tell the person to try again, nothing was erased) | 422 confirm missing. After ok:true: sign out locally (supabase.auth.signOut may fail because the session is gone: ignore the error), clear caches, route to a short "Your account was deleted" page.
- The disable state: read it from the person's own profile data via the existing own-profile read path (find it; `is_active` false = hidden). Show a clear banner on the account home when hidden.
- Existing: sign out already exists (useAuth); reuse it. Look at src/pages/Account.tsx, src/components/account/*, src/modules/organiser/home/onboarding/SignOutLine.tsx, src/hooks/useAuth.tsx, and the dancer-first gate (src/components/account/DancerProfileGate.tsx): the gate must not trap a person who wants to disable or erase; settings must be reachable from the account menu for any signed-in account, including one with an unfinished profile.
