# P3 field inventory: admin event editor vs the organiser dashboard

## 0. Header

- **Purpose.** This is the input the organiser mock-ups lacked. It lists every concept the admin event editor (`components/events/editor-v2/`) has. For each one it says whether organisers need it, in which wave, whether C2 already draws it, and which organiser write path exists today. C3 keeps C2's look and must reach parity with this list for everything organisers own (brief: `docs/organiser-rebuild/p3/R-FIELD-INVENTORY.md`).
- **Prod query date:** 2026-10-23 18:41 UTC (read-only SELECTs, counts only). The write-path and catalog facts were read from the live prod catalog on the same day.
- **Branch:** `claude/er-p3-field-inventory`. Research only: no source edits, no Supabase writes.
- **Sources:** all 78 files under `components/events/editor-v2/` (24,252 lines); `docs/organiser-rebuild/p3/mockups/C2.html` + `C2.md` + `DESIGN-COMMON.md`; `docs/architecture-p5.md`, `docs/db-contracts.md`, `docs/program-lineup-playbook.md`, ADR-005, ADR-007, `docs/event-editor-phase-5-decisions.md`; the prod catalog (`pg_proc`, `pg_policy`, grants) and prod counts.
- **Inputs merged here:** four editor row sets (identity / lifecycle / schedule / time / conversion; programme / sessions / per-date; content / venue / money / media / promotion; save model + read / write path), the C2 inventory, the write-path / history / stats / venue / profile slice, and the prod-shape slice.
- **How to read the matrix.** `#` is stable inside this document. File paths in "where" are under `components/events/editor-v2/` unless they start with `components/`, `lib/` or `docs/`. "C2.html:N" is a line in the C2 mock-up. "owner keys" means the keys a signed-in organiser (series owner or manager, not an admin) may send today.

## 1. Verdict

1. **Size.** `components/events/editor-v2/` is 78 files and 24,252 lines (`find -type f`; the brief's 82 counts the 4 directories too), plus the canvas session card it mounts.
2. **Concepts.** 158 editor concepts in the matrix plus 44 in data but not in the editor = 202. C2 fully covers 15 of the 142 MUST rows. The GAP LIST has 127 lines.
3. **Matrix needs (158 rows).** MUST-W1 113, MUST-W2 5, MUST-W3 4, LATER 16, ADMIN-ONLY 13, NOT-ORGANISER 7. In-data rows: MUST-W1 14, MUST-W2 4, MUST-W3 2, LATER 11, ADMIN-ONLY 4, NOT-ORGANISER 9.
4. **What a flat line-up per date hurts most.** (a) sessions, each with its own kind and time (#69, #72, #75); (b) people per session, with a role (#94, #95); (c) one-date session changes vs every date (#87, #88, #89); (d) level per session (#114); (e) the event start and end, which are derived from the sessions (#48, #49).
5. **Biggest blockers for C3 / phase 4.** No organiser "this and later" path exists, and programme changes cannot go forward on the server at all (#87, #135). Duplicate, convert, group chat, history and stats have no organiser write or read path. Organisers can still send a city despite answer 20 (section 4c).

## 4. The sessions model, spelled out

**Stored.** The every-date programme is the series template: `event_series_program_day_p5` > `event_series_program_section_p5` (kind) > `event_series_program_item_p5`. An item holds title, type, start / end, `venue_room_id` + legacy room text, levels, style, theme, sort_order and parallel_group_id. People live in `event_series_program_people_p5` (profile_id, profile_type, role, optional level). `series.set_program` writes the whole template in one go as a FULL REPLACE, people included. Per-date changes go to two P5 tables. `event_occurrence_session_override_p5` holds a sparse patch, or `cancelled`, on one template session for one date. `event_occurrence_added_session_p5` + `_people_p5` hold a session that exists on one date only. `occurrence.set_session_delta` writes both, with the deltas `override` / `added` / `remove_added` / `clear_override`. Organisers reach the per-date side through `organiser_set_occurrence_programme_v1`.

**Read.** A date's effective programme is the template, minus sessions cancelled on that date, with that date's overridden fields applied, plus that date's added sessions. It is ordered by sort_order, then start time (ADR-007). The public per-date programme reads P5 through `get_occurrence_program_v1`. The admin series view shows only the template, so it needs a separate note for date-only sessions (#91). Each series session also lists the dates that pin their own version (#92).

**ONE date vs ALL dates.** Adding a session to ONE date is an `added` delta. It applies the moment you press Add, comes with an Undo (`remove_added`), and can never widen to other dates (`save/scopeEligibility.ts:29-33,84`). Adding to ALL dates means editing the series programme and saving. `series.set_program` rewrites the template, but a date that already pins its own version of a session keeps it.

**Finding: programme changes cannot go "this and later" on the server today.** Sessions, line-up, levels, rooms and session times change for this date only or for the whole series (`save/scopeEligibility.ts:16-17,125`). The editor's workaround is to change the whole series, then re-set the dates that should differ (`ScopeDialog.tsx:263-265`). This clashes with owner answer 3 ("this date only / this and later" at launch) and with C2's line-up scope sheet (C2.html:850-856). Only description, cover, ticket link, level and venue (+ city) can go forward, and even those go through `series.apply_forward_from`, which is admin-only. So an organiser has no "this and later" path for anything today (section 4c). `organiser_set_occurrence_programme_v1` locks the series row, so two organisers saving different dates of one series wait for each other (`docs/db-contracts.md:166,251-253`).

**Traps a designer must not draw wrong.**
1. **Status comes from data.** A date's `lifecycle_status` is only scheduled or cancelled, and nothing writes "past". "Done" comes from `is_completed`. The event's type (party / class / masterclass) is DERIVED from session kinds, so never draw a picker for it.
2. **Time.** Session times are London wall clock stored as if UTC ("local-as-Z"). The series headline time is true UTC, so never mix the two. A session can end after midnight ("ends next day"). A date has no time of its own, so moving one date's time shifts its sessions. On a date with no session, the server creates a hidden `sort_order -1` session. The headline start time and the repeat rule are series-only.
3. **Cancel is not remove.** Cancelling a series session on one date keeps it, struck through, as an override row. Removing a date-only session deletes it. Deleting a series session takes it off EVERY date. Cancelling a whole DATE uses `occurrence.cancel` with a public reason. Skipping a date leaves a tombstone in `removed_dates` and deletes that date's own line-up, timings and added sessions. "Reset all" on a date clears detail fields only, and sessions survive it.
4. **Empty is not inherit.** On a date, `[]` (no gallery, no passes) is a real value. An emptied description pins an empty text.
5. **Levels and rooms.** Levels apply to class and masterclass only. Rooms show only when the venue has 2+ rooms. A venue change clears rooms that are not at the new venue unless the UI warns first (#102).
6. **Prod reality.** Party dates mostly run 2-5 sessions (1,823 dates), and 189 run 6 or more. Class dates run 1-4. Teachers sit on sessions (283 people rows on 188 sessions). A flat line-up per event (C2.html:992) cannot hold "class teachers at 8pm, DJ at 10pm".
