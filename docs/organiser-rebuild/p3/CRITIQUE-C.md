# P3 independent critique of mockup C "Today first" (Design Gate stage 5)

Reviewer: independent worker (did not build C). Inputs: brief `R-C-critique.md` (blob 5d19f0b), `DESIGN-COMMON.md`, `M-C-today.md`,
`claude/er-p3-mock-c:docs/organiser-rebuild/p3/mockups/C.html` + `C.md`, A/B for comparison, `origin/main` `ember.css`,
`p2/AUDIT-foundation.md`. Line numbers below are `C.html` lines on `claude/er-p3-mock-c`.

## 1. Verdict

**C is a sound base.** The shell (Next up -> Needs you -> stats -> list, 4 tabs, date strip + "this date only / this and later") is clear, tokens pass contrast in both themes, every target is >= 44px, nothing scrolls sideways. Keep the structure; v2 is about wording, the two stubbed creates, and four places where C would show dancers wrong information.
**Must-fix 1:** one word for "cancel a date" everywhere (today: "Cancel this date" / "Take it off" / "Off" / "Cancelled") and say the year in full ("Jan 27" reads as 27 January).
**Must-fix 2:** the wrong-info paths: "This and later ones" counts dates already off and promises "to the last one" on a weekly with no end; "Move ... this and later ones" asks for ONE new date and then toasts a hard-coded "Moved to Thu 29 Oct"; the "Add the teachers for the November course" task opens tonight's Friday line-up.
**Must-fix 3:** design the flows C stubs or omits: weekly social and one-off party create (toast "Shown in mockup A and B"), How to pay, Where/venue, ticket link, and the invitee's first screen.

## 2. Ordered fix list (most material first)

1. **Event page > date sheet > "This and later ones" (L664, L668-670) - wrong count, wrong promise.** `dates.length - dateIdx` counts dates already taken off: on Sensual Wednesdays, tapping Wed 2 Dec -> "This and later ones: 6 dates, to the last one" -> "Take 6 dates off?" but 2 of those (23, 30 Dec) are already off (measured). A weekly social has no last date, so "to the last one" is false. **Fix:** count only dates still on; for an event with no end say "Every Wednesday from 2 Dec on (no end date)"; for a course say "4 classes, to Wed 27 Jan 2027". **Why:** the organiser decides from that number; a wrong one makes them doubt every number on the page.
2. **Move > "This and later ones" (L455-461, L768-769, L791) - wrong info goes public.** Choosing "this and later ones" lands on a screen with one "New date" field (a single day) and the toast always says "Moved to Thu 29 Oct" whatever was moved (measured: moving Wed 11 Nov later -> "Moved to Thu 29 Oct"). **Fix:** for "this date only" keep New date + Starts at; for "this and later ones" ask "Which day of the week now?" (7 big choices) + "Starts at", and echo the real result: "From Wed 11 Nov: Thursdays, 8pm. 6 dates moved." Hint line under the field must use the picked values. **Why:** the owner's top fear is wrong info shown publicly; this is a direct path to it.
3. **Line-up screen header is fixed to "Fri 23 Oct - Sensual Fridays" (L417) and reached from 4 places** (Home quick action L313, Needs-you "Add the teachers for the November course" L322, event page row L620, course check step L531, date sheet L656). Measured: the teachers task opens Friday's line-up. **Fix:** line-up always carries its event + date(s) in the header ("Sensual Wednesdays course - all 6 classes" / "Fri 23 Oct only"); from the course task and the course check step default to "every class"; from the event page row ask the same "This date only / This and later ones" as the strip. **Why:** a low-tech organiser will add teachers to the wrong night and never notice.
4. **Same action, four words (L312 "Cancel this date", L657 "Take it off", L615 strip "Off", L657/L670 dancers see "Cancelled", L618 "taken off").** **Fix:** one verb pair in one labels file: action "Cancel this date" / "Cancel these dates", state chip "Cancelled", undo "Bring it back". Same on Home, strip, sheets, toast, legend and public preview. **Why:** "Take it off" can read as "delete" or "hide the event"; the same thing must have the same name everywhere (DESIGN-COMMON quality bar).
5. **"Jan 27" for 2027 (L560, L571, L618; strip chips; legend "Last: Wed 27 Jan 27").** In a chip "6 / Jan 27" reads as 27 January; the legend "Wed 27 Jan 27" is unreadable. Course create already says "6 Jan 2027" (L747), so two formats exist. **Fix:** chips show month only and a small "2027" year marker on the first chip of a new year; text always "Wed 6 Jan 2027" (one shared date formatter, closes G20/W6). **Why:** a misread date = dancers turning up on the wrong night.
6. **"Add an event or course" sheet stubs two of three choices (L683-684: toast "Shown in mockup A and B").** The weekly social is the brief's main event type, and prod has live one-offs (NYE Masquerade Ball, Halloween Edition). **Fix:** build both in C's StepFrame: weekly = name -> which day + start time -> where -> how to pay -> check -> live; one-off = name -> date + time -> where -> how to pay -> check -> live. Reuse the course steps (L485-535) so all three flows share step count and wording. **Why:** an organiser who taps "A weekly social" and gets a toast thinks the app is broken.
7. **No "How to pay", "Where" or ticket link editing anywhere, yet the public preview shows "How to pay: GBP 12 on the door, card or cash" (L477-478).** Prod: every live LLB event has a ticket link and none has payment methods set. **Fix:** add three rows to "About this event" (L619-624): Where (venue picker with "Not listed? Add it"), How to pay (tick: on the door cash / card / online link), Ticket link; the preview shows only what those rows hold, and "Not set yet - add it" (to the organiser only) when empty. **Why:** the preview must never show information the organiser cannot see or change.
8. **Cancelling tonight leaves Home unchanged (L305-317, L771-779).** Measured: after "Yes, cancel tonight" the hero still says "Live - Next up - Tonight, 8pm" with the same three actions; only a 10 s toast proves it worked. Same for Pause (L674): the event tag stays "Live". **Fix:** hero swaps to a "Cancelled tonight" state (red chip, line "Dancers see Cancelled", one action "Bring it back"), and "Next up" moves to the next live date below it; paused event shows the Paused chip and its own "Turn back on" primary. **Why:** low-tech users trust what they see on the screen, not a toast that vanished.
9. **The Undo toast covers the Events primary button for 10 s (L249 toast `bottom:96px` vs L349 bottombar `bottom:80px`).** Measured in both themes: after cancelling tonight, the "Add an event or course" button on Events cannot be tapped until the toast goes. **Fix:** toast sits above whichever bar is showing (compute from the bottombar + tab bar height), or the bottombar lifts while a toast shows. **Why:** a dead button reads as a frozen app.
10. **Keyboard open hides line-up search results (L420-424).** Simulated Android keyboard (layout viewport 390x514): the input sits at 361-413, results start at 423 and the "Nothing changed yet" bar sits at 426, so every match is under the bar (screenshot `kbd-lineup_search`). **Fix:** hide the bottombar while the search input has focus (or put Save in the top bar on this screen), and scroll results into view. Same rule for every screen with an input and a bottombar (course name, place, move, invite). **Why:** the organiser types a name and sees nothing; they will think the person does not exist.
11. **Line-up "changed" is a length check (L731).** Measured: remove DJ Kizzy, add Sofia Ramos -> button stays disabled "Nothing changed yet"; the swap cannot be saved. **Fix:** compare the set of people, not the count. **Why:** swapping a DJ is the most common line-up change.
12. **Saves are shown as fact, but there is no saves data (L310, L329, L362, L366, L651).** A and B both note no saves table exists (G49); "42 people saved tonight" is in the cancel sheet. "Numbers update every hour" (L366) is unverified. **Fix:** v2 shows views only until a saves source exists, or labels it clearly as coming soon; drop the update-frequency claim until the stats RPC is built. Also pick one word: "people saw" (L328) vs "Seen by" (L623) vs "seen" (L597) - use "views" unless distinct viewers are really counted. **Why:** an organiser who quotes a wrong number to a venue loses trust in the tool.
13. **First day lists 3 events + "+4 more" = 7; Team says "All 6 events" (L295, L446-447).** The "+4 more" row is not tappable and wears the "No photo yet" stripe. **Fix:** list every matched event (name, day, venue) with a per-row "Not mine" link; count once from one source; give the "+N more" row a chevron that expands. **Why:** day one is when a wrong match is cheapest to catch; a hidden match goes live under the wrong organiser (owner fear: wrong info public).
14. **Sensual Wednesdays is a course on prod but C shows it as "Weekly social" with an open-ended strip (L559-561); Mambo City x LLB is live monthly on prod but shown paused (L347); Sensual Saturdays starts 8pm on prod, C says 9pm (L564).** **Fix:** v2 data from a prod read (names, format, start time, venue); show a monthly event too (strip with one chip per month). Prod also has two live events both called "Sensual Wednesdays": the list needs a second line that tells them apart (dates "4 Nov - 2 Dec" vs "from 6 Jan"). **Why:** the owner judges the design against data they know by heart; real shapes catch layout bugs (CLAUDE.md real-data rule).
15. **Invite journey has no first screen for the invitee (L686-691, L803).** C stops at "Invite sent". The brief asks for it. **Fix:** add "Jess invited you to run London Loves Bachata's events" -> one primary "Join" -> lands on Home with a one-line "You can now change everything Jess can". Also show what the inviter sees while waiting ("Waiting for them to join - Send again / Cancel invite"). **Why:** if the invitee's first screen is a login wall with no context, they ignore it.
16. **Home has three equal-weight actions and no single primary (L311-315).** On 360x640 the hero + actions use 64-407px of a 560px area; "Needs you" shows one row. **Fix:** keep the 3-up, but make the most likely job (Change line-up) visually primary (filled), and move "Cancel this date" to a quiet text button under it to avoid accidental taps; shrink the cover to 96px on screens under 700px tall. **Why:** one primary per screen; and a big "Cancel" tile one tap from opening the app is the riskiest button on the screen.
17. **Line-up "No one called X" is a dead end for people without a profile (L740).** **Fix:** borrow B's "Add their name anyway" (shown as plain text on the public page, no link) next to the join link. **Why:** most guest DJs have no profile yet; the organiser must still be able to name them.
18. **Help "Stuck? Message Ricky on WhatsApp" has no button (L704); help rows are not tappable.** **Fix:** a real "Message us on WhatsApp" button (wa.me link). **Why:** every help/error state must say AND offer what the person can do.
19. **"Back to editing" in the preview bar (L467) returns to Home when opened from Home** (measured). **Fix:** label it "Back" or "Done". Also unify the three names of this screen: "See page" (L314), "See what dancers see" (L537), "What dancers see" (L467) -> "See what dancers see" everywhere. **Why:** same thing, same name.
20. **Photos screen reached from one event shows every event (L428-437)** and "Add" goes live with no preview. **Fix:** from an event page open that event's photos only; after picking, show the photo as the cover with "Use this photo" / "Pick another". **Why:** they see what dancers will see before it goes live.
21. **Course check step (L527-532): "Teachers: Add later if you like" opens Friday's line-up (see 3), and there is no price / how to pay / level step.** **Fix:** add "How to pay" and "Who is it for (beginners / improvers / all)" steps, both skippable with a reason. **Why:** price and level are the first two things dancers ask about a course.
22. **"8-week course with 13 dates" (L382, L570-572) contradicts itself** (13 chips, 2 off, 1 moved). **Fix:** make the long-name case an 8-class course with 10 chips (2 off) and show "8 classes" in the legend. **Why:** a mockup that miscounts trains the build to miscount.
23. **Empty home (L387-409) has a Back button and no tab bar, and "Add a photo" appears twice (todo row + primary bar).** **Fix:** render it as the real Home with tabs; keep one "Add a photo" (the bottom primary) and make the todo row open the same flow without repeating the words. **Why:** a new organiser must see the same home everyone else gets.
24. **Event page "Live" tag is hard-coded (L610)** for every event, including a paused one opened later. **Fix:** chip from the one shared status mapping (Live / Paused / Ended / Cancelled tonight). **Why:** CLAUDE.md "one shared mapping for any fact shown on more than one screen".
25. **Tab bar on small phones / keyboard.** At 360x640 the 4 tabs fit (90px each, 13px labels, 0 small targets measured) - fine. With the keyboard open, tab screens have no inputs in C so the bar never rides up today; v2 must hide the tab bar while any input is focused (stats search, events filter if added). **Why:** a tab bar floating over a keyboard eats a third of a 640px phone.

## 3. Borrow from A / B (structure of C unchanged)

2. **A: one row each for Where / How to pay (tick all that apply) (A L346-347, L518).** Goes into C's "About this event" card. Fixes item 7 with a pattern already designed.
3. **B: "Next" that says why it is disabled ("Pick one to carry on")** in C's course/weekly/one-off StepFrames. No silent dead buttons (G28/G32).
4. **B: "Add their name instead" in the line-up picker.** Goes under C's "No one called X" (item 17).
5. **B: Change photo right on the cover (HeroCover + ChangePhotoButton).** Put the button on C's event-page cover; removes the detour through the all-events Photos screen (item 20).
6. **A: delete is "Ask us" (admin only), Pause is the only off switch.** C already has Pause; add A's quiet "Want it gone for good? Ask us" line under it so organisers never look for a delete button.
